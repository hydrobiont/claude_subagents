# Dashboard and Logs

## Pages and URLs

- Project root: `https://www.odoo.sh/project/dataegret`
- Builds listing (all branches, most recent first):
  `https://www.odoo.sh/project/dataegret/builds`
- A single branch's build history and Logs tab:
  `https://www.odoo.sh/project/dataegret/branches/<branch>/logs` —
  percent-encode a slash inside a branch name as `%2F`
  (`dev/my-feature` → `dev%2Fmy-feature`).

  **Do not trust this URL pattern blindly.** On 2026-09-09, a slash-named
  branch's constructed URL fell through to production's own build history —
  the plain path did, and so did a `%2F`-encoded version that had worked on
  an earlier date; the application rewrote the address back to its
  unencoded form and served production again. Treat any URL you build by
  hand as a guess, not an address: after navigating, read the page's own
  **heading** (it prints the branch name) to confirm you are actually
  looking at the branch you intended, and prefer clicking the branch in the
  sidebar's branch list over typing a URL. This matters beyond cosmetics —
  the same page carries the **Rebuild** and **Merge** controls, and both
  act on whatever branch the page is actually showing, not the branch named
  in the URL bar.
- Per-build links — **Connect**, **Shell**, **SSH** (the exact `ssh`
  command with that build's id and domain filled in), **View errors** —
  are generated by the dashboard for each build card and are not addresses
  you can construct; open them from the card itself.

## Card anatomy

Each build card on `/builds` or a branch's history shows:

| Element | What it tells you |
|---|---|
| Commit message | which change this build is |
| Age | time since the build was created |
| Duration | how long the build took to run |
| Status word | `Test: Warning`, `Test: Success`, `Test: Failed`, plus a sub-status like `done` |
| Result badge | a colour keyed to the status word — **not** reliable evidence on its own (see Badge semantics) |
| View errors | opens a WARNING-and-above log panel for this build |
| Connect | single-sign-on link into this build's own database |
| Rebuild | discards this branch's current database and rebuilds — on a staging branch this re-forks production; see `references/staging-and-production.md` |

## Log viewer behaviour

The Logs tab's web viewer loads the **tail of `install.log` first** and
only fetches earlier lines as you scroll up. A read that only looks at what
initially renders is equivalent to running `tail` on the container — it
silently drops the install phase and early module-loading output. Always
either scroll to the top before concluding a phase produced no output, or
read the file over SSH/Shell and grep the whole thing.

Over SSH or the Shell tab, the same file trips naive binary-content
detection in some tools (a `docutils` RST-rendering artefact and other
encoding quirks in the log), so use `grep -a` rather than plain `grep`.

## Exact grep patterns

Run these against the whole file, never a tail:

```
# The run's overall tally (all tests, including post_install-tagged ones)
grep -aE "odoo\.tests\.result:" install.log

# Per-module test counts — confirm your module's tests actually ran
grep -aE "odoo\.tests\.stats: <module>:" install.log

# Any ERROR-level line logged during the run — odoo.sh fails a module on
# the presence of one of these regardless of the tally above
grep -a " ERROR " install.log

# Explicit failure/error markers on individual tests, with traceback context
grep -aE "FAIL:|ERROR:" install.log -A 22
```

Replace `<module>` with the technical module name (`de_fin_mail`,
`de_slack_notify`, …). The house one-line combined pass, for a quick skim
of a log you already expect to be clean:

```
grep -aE "<module>: [0-9]+ tests|failed, [0-9]+ error|FAIL:" install.log | tail
```

Drop `| tail` and read the whole match set when you are actually chasing a
failure rather than skimming a known-good log.

One benign, recurring false hit: a line matching `<string>:NN: (ERROR/3)
Unexpected indentation.` is `docutils` complaining about RST formatting
inside a manifest's `description` field. It is pre-existing noise present
on green builds too — confirm it is *that exact* docutils shape before
treating any `ERROR` grep hit as a finding.

## Badge semantics, with the evidence

For this project's modules, **`Test: Warning` with sub-status `done` is the
healthy result** — these modules produce several expected install-time
warnings, so `Test: Success` is not a "more passing" state than `Warning`;
it is simply a build that happened not to log any warnings.

`Test: Failed` does not mean what it says by itself. Confirmed case: build
`38535645` (`de_fin_mail`, 2026-09-23) reported `0 failed, 0 error(s) of
190 tests` in `install.log`, with `de_fin_mail: 34 tests` all accounted
for, and the only ERROR-level lines anywhere in the log were two lines the
module's own guard methods logged **on purpose** — each one exercised by a
test asserting that the guard fires. The build's status card still read
"At least one test failed when loading the modules." odoo.sh judges a
module failed on the presence of an ERROR-level log line during its tests,
full stop, independent of what the test runner's own pass/fail tally says.
The fix, applied in commit `025af82`, was to wrap the deliberate
error-producing call in `self.assertLogs("<logger>", level="ERROR")`,
which both asserts the line fired and keeps it out of the log odoo.sh
scans; the rebuilt badge went green.

The status card's own failing-module list is separately unreliable: on
2026-08-25, one build named a module in that list for which no test
anywhere in the log had actually failed.

## The ERROR-line rule

Because of the above, treat "did this module's tests pass" as two separate
questions, and answer both: (1) what does `odoo.tests.result:` and the
module's own `odoo.tests.stats:` line say, and (2) does ` ERROR ` appear
anywhere in the log during that module's test run, deliberate or not. A
clean tally with a stray ERROR line is still a failed build by odoo.sh's
own rule, even though nothing in the tally shows it.

## Reading the dashboard as a browser-automation agent

The odoo.sh dashboard is a single-page application: navigating to a URL
(constructed or clicked) does not guarantee the visible DOM matches that
address yet.

1. **Wait for the app, not just the network response.** Wait for a stable
   element specific to the page you expect (the build-card list, the log
   pane) rather than acting immediately after navigation.
2. **Read text with an evaluated `innerText`**, not a raw HTML dump — the
   framework re-renders, and a static fetch of the page source will not
   contain what the user actually sees.
3. **Check the heading before reading anything else on the page.** It is
   the one element on a branch page that reliably names which branch you
   are looking at (see the URL trap above); read it first, every time,
   before quoting a build id, a status word, or a log line from that page.
4. **The persistent browser profile can be locked by another session** (a
   `SingletonLock` file names the holding process). Check for that before
   retrying a failed navigation in a loop — correctly refuse to kill a
   foreign process or silently fall back to an isolated profile; ask the
   user to release the session instead.
