### Bulk-load tuning — the verified source/doc map (checked 2026-09-15, REL_18_6)
The canonical doc page is **docs/18/populate.html** (`doc/src/sgml/perform.sgml` §`id="populate"`) — it already carries disable-autocommit, use COPY, drop indexes, drop FKs, raise maintenance_work_mem/max_wal_size, disable archiving+streaming, ANALYZE afterwards, and the pg_dump notes; quote it rather than re-deriving. GUC contexts/defaults at REL_18_6 `guc_tables.c`: maintenance_work_mem USERSET 64MB, work_mem USERSET 4MB, max_parallel_maintenance_workers USERSET 2, max_parallel_workers USERSET 8, synchronous_commit USERSET on, effective_io_concurrency USERSET **16** (17: 1); max_wal_size SIGHUP 1GB (`DEFAULT_MAX_WAL_SEGS 64` × 16MB, xlog_internal.h:92), checkpoint_timeout SIGHUP 300s (max 86400), checkpoint_completion_target SIGHUP **0.9 already in PG 14** (not an 18 change — verified value-for-value 14→18), full_page_writes SIGHUP on, autovacuum SIGHUP on; wal_compression **SUSET** off — enum pglz/lz4/zstd **since PG 15**, plain boolean in 14; shared_buffers/wal_buffers/wal_level/max_wal_senders/io_method POSTMASTER. **wal_level=minimal is enforced against replication in code**: `postmaster.c:852` `if (max_wal_senders > 0 && wal_level == WAL_LEVEL_MINIMAL)` → FATAL "WAL streaming (\"max_wal_senders\" > 0) requires \"wal_level\" to be \"replica\" or \"logical\"", doc mirror at config.sgml guc-wal-level ("the server will not even start in this mode if max_wal_senders is non-zero") which also lists the six operations that trigger the skip (ALTER…SET TABLESPACE, CLUSTER, CREATE TABLE, REFRESH MATVIEW w/o CONCURRENTLY, REINDEX, TRUNCATE); the gate itself is `RelationNeedsWAL()` (rel.h, "false if wal_level = minimal and this relation is created or truncated in the current transaction", design doc `src/backend/access/transam/README` §"Skipping WAL for New RelFileLocator"), and since **PG 13** the commit-time choice is `wal_skip_threshold` (USERSET, default 2MB — smaller ⇒ WAL it, larger ⇒ fsync the files). **COPY FREEZE** is independent of wal_level: the only checks are in `copyfrom.c:864-908` — not partitioned, not foreign, `ThereAreNoPriorRegisteredSnapshots() && ThereAreNoReadyPortals()`, and `rd_createSubid == GetCurrentSubTransactionId() || rd_newRelfilelocatorSubid == …` → "cannot perform COPY FREEZE because the table was not created or truncated in the current subtransaction"; it sets `TABLE_INSERT_FROZEN`, whose **only other caller is `matview.c:495` (REFRESH MATERIALIZED VIEW)** — there is no frozen path for INSERT…SELECT. **COPY vs INSERT write path**: COPY buffers `MAX_BUFFERED_TUPLES 1000`/`MAX_BUFFERED_BYTES 65535` (copyfrom.c:63,69) → `table_multi_insert` (one `XLOG_HEAP2_MULTI_INSERT` per page, heapam.c:2567) and takes `GetBulkInsertState()` → `GetAccessStrategy(BAS_BULKWRITE)` = a **16MB ring** (`freelist.c:602-604`), so shared_buffers barely matters for COPY; INSERT goes one tuple at a time via `nodeModifyTable.c:1234 table_tuple_insert`, and multi-insert is dropped (`insertMethod = CIM_SINGLE`) for BEFORE/INSTEAD-OF triggers, non-batching FDW targets, volatile defaults or volatile WHERE. **FK re-add cost**: `tablecmds.c:validateForeignKeyConstraint()` → `RI_Initial_Check()`, which temporarily sets `work_mem := maintenance_work_mem` and `hash_mem_multiplier := 1` for one LEFT JOIN check query (`ri_triggers.c:1686-1710`) — so maintenance_work_mem, not work_mem, sizes FK validation. Parallel index-build AM coverage by version (config.sgml max_parallel_maintenance_workers): **14/15/16 B-tree only → 17 B-tree+BRIN → 18 B-tree+GIN+BRIN**; workers need ≥32MB each plus 32MB for the leader (create_index.sgml), and `ALTER TABLE … SET (parallel_workers)` bypasses the cost model. `ALTER TABLE … SET LOGGED` always rewrites: `tablecmds.c:18981 tab->rewrite |= AT_REWRITE_ALTER_PERSISTENCE`; unlogged tables "are also not replicated to standby servers" (create_table.sgml UNLOGGED). **Parallel COPY does not exist in any release** — commitfest 30/2610 "Support parallelism for copy command" is **Withdrawn** (2021-03), thread `CAA4eK1+kpddvvLxWm4BuG_AhVvYz8mKAEa7osxp_X0d4ZEiV=g@mail.gmail.com`; and parallel.sgml is explicit that a data-modifying top-level query gets no parallel plan, CTAS/SELECT INTO/CREATE MATVIEW being the only exceptions — so INSERT…SELECT is single-backend too. **PG 18 specifics that do NOT change a bulk load**: AIO is reads-only (see the AIO entry), and the only 18 checkpointer changes are monitoring (`pg_stat_checkpointer.num_done`, `slru_written`, split log line) — no checkpoint algorithm or default changed. What does change: effective_io_concurrency/maintenance_io_concurrency 16 (release-18 commits ff79b5b2a, cc6be07eb), eager freezing via `vacuum_max_eager_freeze_failure_rate` 0.03, `vacuumdb --missing-stats-only`, and PG 17's TidStore removing the old 1GB dead-item cap on vacuum's maintenance_work_mem (the `Assert(max_items <= MAXDEADITEMS(MaxAllocSize))` present in REL_16 `vacuum.c:2578` is gone in 18).

### Patroni facts a PostgreSQL answer keeps needing — and the registry gap (checked 2026-09-15, patroni.readthedocs.io/en/latest)
**Patroni is NOT in `TRUSTED_SOURCES.md`** — cite its docs as a project-own external source with a retrieval date and flag the gap. `patroni_configuration.html` §"Important rules": `wal_level` is a Patroni-controlled parameter with "default value hot_standby, accepted values: hot_standby, replica, logical" — **`minimal` is not an accepted value**, and for that group "values set either in the local patroni configuration files or via the environment variables take no effect" (they must go in the DCS); `max_wal_senders` ("default value 10, minimal value 3") and `max_replication_slots` ("default 10, minimal 4") are restricted to dynamic configuration. So the `wal_level=minimal` + `max_wal_senders=0` bulk-load trick is structurally unavailable on a Patroni cluster, independent of the PostgreSQL-side `postmaster.c:852` FATAL. `replication_modes.html`: `synchronous_mode` "will not promote a standby unless it is certain that the standby contains all transactions that may have returned a successful commit status"; `synchronous_node_count` default 1; `synchronous_mode_strict` "prevents Patroni from switching off the synchronous replication on the primary when no synchronous standby candidates are available"; and the money quote for per-session tuning — "Clients can change the behavior per transaction using PostgreSQL's `synchronous_commit` setting. Transactions with `synchronous_commit` values of `off` and `local` may be lost on fail over, but will not be blocked by replication delays." That matches PG's own config.sgml (`local` = local flush only, no replication wait; `off` = no wait at all, max delay 3 × wal_writer_delay, no risk of inconsistency) and high-availability.sgml ("synchronous_standby_names specifies the number and names of synchronous standbys that transaction commits made when synchronous_commit is set to on, remote_apply or remote_write will wait for responses from").


### Django + psycopg 3 prepared statements — `server_side_binding` alone is NOT enough (checked 2026-09-15, Django 5.2 LTS and 6.1)
The decisive file is `django/db/backends/postgresql/base.py:DatabaseWrapper.get_connection_params()`, **byte-identical at tags `5.2` and `6.1`**: under `if is_psycopg3:` it sets `conn_params["prepare_threshold"] = conn_params.pop("prepare_threshold", None)` with the verbatim comment "Disable prepared statements by default to keep connection poolers working. Can be reenabled via OPTIONS in the settings dict." So Django **forces psycopg's `prepare_threshold` to `None` (preparation off)** unless the app puts `prepare_threshold` in `OPTIONS` — separately from `server_side_binding`, which only swaps the cursor factory (`ServerBindingCursor` = psycopg `Database.Cursor` when `server_side_binding is True`, else `Cursor` = `Database.ClientCursor`). Getting server-side prepared statements out of Django therefore needs **both** OPTIONS keys. Release state on 2026-09-15 (djangoproject.com/download/): latest **6.1.1**, current LTS **5.2** (5.2.17, extended support to April 2028); 6.1 requires PostgreSQL 15+ / psycopg 3.1.12+ where 5.2 requires PostgreSQL 14+ / psycopg 3.1.8+ — the `server_side_binding` prose in `ref/databases/` is identical in both. **Fetch mechanics: psycopg.org returns HTTP 403 to WebFetch** — read psycopg docs from `raw.githubusercontent.com/psycopg/psycopg/<tag>/docs/...` instead (latest tag 3.3.5; `docs/advanced/prepare.rst` carries the PgBouncer≥1.22 + `max_prepared_statements`>0 + libpq 17 triple and the `prepared_max = None` fallback, `docs/basic/from_pg2.rst` the server-side-binding costs, `psycopg/psycopg/_preparing.py` the defaults `prepare_threshold: int | None = 5`, `prepared_max: int = 100`).

### Rails/Active Record prepared statements through a pooler — the source map (checked 2026-09-15, rails v8.1.3.1)
Three files settle every Rails-behind-PgBouncer question, all cited at tag `v8.1.3.1`. `activerecord/lib/active_record/connection_adapters/abstract_adapter.rb:default_prepared_statements()` returns `true` (the `prepared_statements` default) and `@prepared_statements` is built from `@config.fetch(:prepared_statements) { default_prepared_statements }`. `connection_adapters/statement_pool.rb` holds `DEFAULT_STATEMENT_LIMIT = 1000` — the `statement_limit` default, a **per-client-connection** cache that must be sized against PgBouncer's **per-server-connection** `max_prepared_statements`. `connection_adapters/postgresql_adapter.rb` carries the protocol-Close switch: `if PG::Connection.method_defined?(:close_prepared) # pg 1.6.0 & libpq 17` wraps `supports_close_prepared?`, which additionally requires `database_version >= 17_00_00`, and `PostgreSQLAdapter::StatementPool#dealloc(key)` branches `conn.close_prepared key` vs `conn.query "DEALLOCATE #{key}"`. So protocol-level Close on eviction needs **ruby-pg ≥ 1.6.0 built against libpq 17, AND a PostgreSQL server ≥ 17, AND Rails ≥ 8.1.0** (`close_prepared` absent at `v8.0.4`) — miss any one and Rails falls back to SQL `DEALLOCATE`, which under PgBouncer tracking always fails `26000` because the backend holds only `PGBOUNCER_<n>` (PgBouncer issue #1041, open).

### PG 18 AIO — process model, defaults, and the packaging answer (checked 2026-09-08, REL_18_6 + PGDG)
`io_method` is PGC_POSTMASTER, **default `worker`** (`src/include/storage/aio.h:42 #define DEFAULT_IO_METHOD IOMETHOD_WORKER`); allowed values come from `src/backend/storage/aio/aio.c:io_method_options[]` = `sync`, `worker`, and `io_uring` **only under `#ifdef IOMETHOD_IO_URING_ENABLED`** (= `USE_LIBURING && !EXEC_BACKEND`). `io_workers` is PGC_SIGHUP, **default 3**, range 1–`MAX_IO_WORKERS` = 32 (`src/include/storage/proc.h:460`). Runtime probe for io_uring support: `SELECT enumvals FROM pg_settings WHERE name='io_method'` — the array is built from that compile-time-conditional list. **PGDG packaging**: Debian/Ubuntu YES on all Linux suites — `debian/control` Build-Depends `liburing-dev [linux-any]`, flag added by postgresql-common `server/postgresql.mk` (`version_ge,18` + linux guard → `--with-liburing`, changelog 277, 2025-04-09), and shipped `postgresql-18 18.6-1.pgdg*` runtime-Depends on liburing1/2. RPMs YES on EL9/EL10/Fedora/SLES but **NO on RHEL/Rocky 8** — `postgresql-18.spec` lines 18-23 set `%global liburing 0` for `%{?rhel} == 8` ("RHEL 8 does not have io_uring support"), and rhel-8 repodata carries no liburing requires. Compiled-in ≠ usable: `method_io_uring.c:pgaio_uring_shmem_init()` raises a startup ERROR with hints "Check if io_uring is disabled via /proc/sys/kernel/io_uring_disabled" (EPERM), "The kernel does not support io_uring" (ENOSYS), or a ulimit -n hint (EMFILE) — undocumented in the SGML docs. **Process model**: two new `BackendType`s in 18, `B_IO_WORKER` and `B_DEAD_END_BACKEND`; none removed or renamed. `GetBackendTypeDesc()` names them "io worker" and "dead-end client backend"; io workers call `AuxiliaryProcessMainCommon()` → `pgstat_bestart_final()` so they DO appear in `pg_stat_activity.backend_type` (ps shows `postgres: io worker N` via `init_ps_display(NULL)` + `set_ps_display(id)`), **even though the docs/18 pg_stat_activity backend_type list omits both "io worker" and "slotsync worker"**. io workers are counted in cluster-wide `pg_stat_io` (`pgstat_io.c:pgstat_tracks_io_bktype()`) but excluded from per-backend stats (`pgstat_backend.c:pgstat_tracks_backend_bktype()`); dead-end backends are excluded from both and never reach pg_stat_activity.

### PG 18 VACUUM/partition/protocol facts worth not re-deriving (checked 2026-09-08, REL_18_6)
**Eager freezing**: `vacuum_max_eager_freeze_failure_rate` default **0.03**, 0 disables; only *failures* count against the cap and successes are separately capped internally at 20% of all-visible-not-all-frozen pages (docs/18/runtime-config-vacuum.html). **Undocumented-in-release-notes behavior change**: `autovacuum_vacuum_insert_scale_factor` is now a fraction of **unfrozen pages**, not table size — `autovacuum.c:relation_needs_vacanalyze()` computes `vacinsthresh = base + scale * reltuples * pcnt_unfrozen` where `pcnt_unfrozen = 1 - relallfrozen/relpages`; docs/17 said "fraction of the table size". **Worker slots**: `autovacuum_worker_slots` PGC_POSTMASTER default 16; `autovacuum_max_workers` moved PGC_POSTMASTER→**PGC_SIGHUP** (default still 3) and silently caps at the slot count. `autovacuum_vacuum_max_threshold` default 100,000,000, -1 disables. `vacuum_truncate` GUC is new (default on) and layers under the pre-existing reloption of the same name; `VACUUM (TRUNCATE …)` overrides both. **ONLY**: PG 17 `expand_vacuum_rel()` recursed only for `RELKIND_PARTITIONED_TABLE` (`include_parts`); PG 18 keys off `vrel->relation->inh`, so plain VACUUM/ANALYZE now also recurse into *legacy inheritance children* and `ONLY` suppresses recursion — `VACUUM ONLY <partitioned>` emits WARNING "VACUUM ONLY of partitioned table \"%s\" has no effect", while `ANALYZE ONLY <partitioned>` still samples all partitions to build the parent's inherited stats and just skips per-partition stats (the post-upgrade fix). autovacuum still never processes partitioned parents. **VERBOSE output deltas**: vacuumlazy.c adds ", %u eagerly scanned" to the pages: line, a whole new "visibility map: … set all-visible, … set all-frozen" line, "delay time: %.3f ms" (gated on `track_cost_delay_timing`, default off), " %lld buffers full" on the WAL usage line, and renames buffer-usage "misses" → **"reads"**; analyze.c's instrumentation block was autovacuum-only in 17 (`AmAutoVacuumWorkerProcess() && log_min_duration >= 0`) and in 18 gains `verbose ||`, so manual `ANALYZE VERBOSE` now prints it at INFO under the header "finished analyzing table". Both progress views gained exactly one column, `delay_time`. **SPLIT/MERGE PARTITION**: absent from PG 18 — no `split` keyword in `kwlist.h`, no grammar; present in REL_19_BETA3 `gram.y` as `SPLIT PARTITION x INTO (…)` / `MERGE PARTITIONS (…) INTO x`. **Protocol 3.2**: `PG_PROTOCOL_LATEST = PG_PROTOCOL(3,2)` but libpq 18 still *requests 3.0 by default* — `fe-connect.c` sets `max_pversion = PG_PROTOCOL(3,0)` unless `min_protocol_version > 3.0`, with the comment "To not break connecting to older servers/poolers that do not yet support NegotiateProtocolVersion". `max_protocol_version`/`min_protocol_version` are libpq connection params + PGMAXPROTOCOLVERSION/PGMINPROTOCOLVERSION env vars, **not GUCs**; values `3.0`, `3.2`, `latest`. docs/18/protocol-overview.html even records that 3.1 was skipped because "old versions of the popular pgbouncer application had a bug in the protocol negotiation".

### PgBouncer vs PostgreSQL 18 (checked 2026-09-08, PgBouncer 1.25.2)
Current release **1.25.2, 2026-05-08** (a 4-CVE security release); changelog file is **NEWS.md**, not CHANGELOG.md, and pgbouncer.org/config.html is built from **master**, not from the release — cite the `pgbouncer_1_25_2` tag for shipping behavior. ### PgBouncer vs PostgreSQL 18 — protocol/auth state (checked 2026-09-08; PgBouncer sources are OUTSIDE the registry)
Standing registry gap: pgbouncer.org and github.com/pgbouncer/pgbouncer are **not** in `TRUSTED_SOURCES.md`, so every PgBouncer claim must be flagged as sourced outside sources 1-5. ### PG 18 AIO is READS-ONLY — the decisive greps, plus io_method/io worker map (checked 2026-09-08, REL_18_STABLE @ b90eeb29eea, post-18.6)

Release note E.6.3.1.3 is explicit: "allows backends to queue multiple **read** requests… sequential scans, bitmap heap scans, vacuums". Two traps: the AIO README's §"IO can be started in critical sections" (lines 197-217) says "Using AIO for WAL writes can reduce the overhead of WAL logging substantially" — that is *design rationale for future work*, not shipped 18 behaviour (`PgAioOp` comment aio.h:95-104 lists fsync/fdatasync/flush_range as "in the near term we'll need"); and `pg_aios.operation` is *documented* with value `writev`, which nothing in 18 can produce. **io_method**: values `sync`/`worker`/`io_uring` (`aio.c:64` io_method_options[]; io_uring compiled in only under `IOMETHOD_IO_URING_ENABLED` = USE_LIBURING && !EXEC_BACKEND, aio.h:26-28); default **worker on every platform**, set at `src/include/storage/aio.h:42` `#define DEFAULT_IO_METHOD IOMETHOD_WORKER` ("We'll default to worker based execution"), wired at guc_tables.c:5431, PGC_POSTMASTER. **Defaults**: io_workers **3** (guc_tables.c:3319, PGC_SIGHUP, max MAX_IO_WORKERS=32 proc.h:460); io_combine_limit and io_max_combine_limit both **128 kB = 16 blocks** (`DEFAULT_IO_COMBINE_LIMIT Min(MAX_IO_COMBINE_LIMIT,(128*1024)/BLCKSZ)` bufmgr.h:167, MAX = PG_IOV_MAX = Min(IOV_MAX,128) pg_iovec.h:47); io_max_concurrency **-1** (auto, capped 64). **effective_io_concurrency / maintenance_io_concurrency: 16 / 16 unconditional in 18** (bufmgr.h:161-162) vs **1 / 10 under `#ifdef USE_PREFETCH`, else 0 / 0 in 17** (REL_17 bufmgr.h:158-164) — release note E.6.3.1.3 "Increase … default values to 16 (Melanie Plageman)". **ps deltas 17→18**: `BackendType` gains exactly `B_IO_WORKER` and `B_DEAD_END_BACKEND` (miscadmin.h:337-368), **nothing removed**; title string "io worker" at `GetBackendTypeDesc()` miscinit.c:296, composed by `init_ps_display(NULL)` ps_status.c:269 (`"postgres: " + desc + " "`, or `"postgres: <cluster_name>: …"` when cluster_name is set — Debian sets `18/main`) then `IoWorkerMain()` method_worker.c:414-415 `sprintf(cmd,"%d",MyIoWorkerId); set_ps_display(cmd)` → `postgres: io worker 0|1|2`. The PG 18 **glossary "Auxiliary process" entry still omits the I/O worker** despite miscadmin.h's comment telling patch authors to update it — live doc gap, don't count processes from the glossary.

### PG 17 read stream vs PG 18 AIO — the version line people blur (checked 2026-09-08)
"AIO's foundation landed in 17, expanded in 18" is misleading and needs restating on any slide. **PG 17 added the read stream / streaming-read API and I/O combining, still fully synchronous**: `src/backend/storage/aio/read_stream.c` + `src/include/storage/read_stream.h` are new in REL_17_STABLE and **absent from REL_16_STABLE** (`git ls-tree origin/REL_16_STABLE src/backend/storage/aio/` returns nothing); PG 17's `src/backend/storage/aio/` holds **only** Makefile, meson.build, read_stream.c. Its own header comment proves the mechanism is `preadv` + `posix_fadvise` hints, not AIO — it builds look-ahead on `StartReadBuffers()`/`WaitReadBuffers()` and branches on whether "fadvise is undesirable … or impossible because direct I/O is enabled or the system doesn't support fadvise". PG 17 release notes carry only E.12.3.1.3 "Allow the grouping of file system reads with the new system variable io_combine_limit" and the E.12.1 overview phrase "sequential reads using streaming I/O"; **`io_method`, `io_workers`, `io_max_combine_limit`, "read stream", "vectored" and "asynchronous I/O subsystem" appear nowhere in the PG 17 release notes or on docs/17/runtime-config-resource.html**. PG 18 is where the AIO subsystem itself lands (aio.c, aio_callback.c, aio_init.c, aio_io.c, aio_target.c, aio_funcs.c, method_sync.c, method_worker.c, method_io_uring.c, the io_method GUC, I/O workers, pg_aios) — release note E.6.3.1.3 "Add an asynchronous I/O subsystem". ### Wire protocol 3.2 + libpq default is still 3.0 — the whole map (checked 2026-09-08, REL_18_STABLE @ e0f5f79d2f6)
The single most-misstated PG 18 fact: **3.2 exists but nothing uses it by default.** `src/include/libpq/pqcomm.h`: `PG_PROTOCOL_EARLIEST PG_PROTOCOL(3,0)`, `PG_PROTOCOL_LATEST PG_PROTOCOL(3,2)`. The default lives in `src/interfaces/libpq/fe-connect.c:pqConnectOptions2()` — when `max_protocol_version` is unset, `if (conn->min_pversion > PG_PROTOCOL(3, 0)) conn->max_pversion = PG_PROTOCOL_LATEST; else conn->max_pversion = PG_PROTOCOL(3, 0);`, with the verbatim comment "To not break connecting to older servers/poolers that do not yet support NegotiateProtocolVersion, default to the 3.0 protocol at least for a while longer." `min_pversion` defaults to `PG_PROTOCOL_EARLIEST` (3.0). Both options are entries in the `PQconninfoOptions[]` table (env `PGMAXPROTOCOLVERSION`/`PGMINPROTOCOLVERSION`, no compiled default, values `3.0`/`3.2`/`latest`). Docs say it verbatim at docs/18/protocol.html §55.2.1: "The current, latest version of the protocol is version 3.2. However, for backwards compatibility with old server versions and middleware that don't support the version negotiation yet, libpq still uses protocol version 3.0 by default", and docs/18/libpq-connect.html max_protocol_version: "The default is to use version `3.0` of the PostgreSQL protocol, unless the connection string specifies a feature that relies on a higher protocol version". **psql 18 therefore speaks 3.0** — `src/bin/psql/startup.c` never sets the option; verify live with `\conninfo`, which gained a "Protocol Version" row via `PQfullProtocolVersion()` (`src/bin/psql/command.c`, PG 18 commit cdb6b0fdb). **3.2's ONLY wire change is the cancel key** (grep protocol.sgml: the sole version-gated sentences are the two "Before protocol version 3.2, the secret key was always 4 bytes long."): BackendKeyData + CancelRequest got a variable-length key, max 256 bytes on the wire; the server generates 32 bytes (`src/include/storage/procsignal.h:MAX_CANCEL_KEY_LENGTH 32`) only under 3.2 — `src/backend/tcop/postgres.c:PostgresMain()` does `len = (MyProcPort == NULL || MyProcPort->proto >= PG_PROTOCOL(3, 2)) ? MAX_CANCEL_KEY_LENGTH : 4;`, so a 3.0 client on an 18 server still gets a 4-byte key. **Negotiation**: server `src/backend/tcop/backend_startup.c:ProcessStartupPacket()` clamps `FrontendProtocol = Min(proto, PG_PROTOCOL_LATEST)` and sends NegotiateProtocolVersion only if the client's minor exceeds its own or options were unrecognized; client `src/interfaces/libpq/fe-protocol3.c:pqGetNegotiateProtocolVersion3()` **hard-fails on a 3.1 offer** ("server requested downgrade to non-existent 3.1 protocol version") — and protocol.sgml's version table says 3.1 was skipped precisely "because old versions of the popular pgbouncer application had a bug in the protocol negotiation which made it incorrectly claim that it supported version 3.1". That bug is the documented reason the libpq default stayed at 3.0.

### PG 18 connection/auth change surface a pooler cares about (checked 2026-09-08, REL_17_STABLE vs REL_18_STABLE)
Deltas verified by diffing `guc_tables.c` and the catalogs, not from release-note prose alone. **`log_connections` changed type**: 17 = boolean `&Log_connections` default `false`; 18 = string `&log_connections_string` with `GUC_LIST_INPUT`, default `""`, `check_log_connections`/`assign_log_connections` (release-18 §Monitoring, commit 9219093ca, "This server variable was previously only boolean, which is still supported" — so `on`/`off` keep working). **`search_path` is the ONLY new GUC_REPORT parameter in 18** — mechanically confirmed by diffing the GUC_REPORT sets of both branches; 17 flags are `GUC_LIST_INPUT | GUC_LIST_QUOTE | GUC_EXPLAIN`, 18 adds `GUC_REPORT` (commits 28a1121fd, 0d06a7eac). ### Release lifecycle / EOL / minor-version facts — page map + 2025-2026 anomalies (checked 2026-08-28)
Where the date-sensitive lifecycle facts live, and the two anomalies that break naive minor-number arithmetic. **Pages**: `postgresql.org/support/versioning/` carries the whole policy verbatim — "a new major version containing new features about once a year", minor releases "at least once every three months", "supports a major version for 5 years after its initial release. After this, a final minor version will be released and the software will then be unsupported (end-of-life)", the recommendation "**We recommend that users always run the current minor release associated with their major version**" plus "The community considers performing minor upgrades to be less risky than continuing to run an old minor version" — AND the support table (version / current minor / supported / First Release / Final Release), which is the single best citation for both GA and EOL dates. `postgresql.org/developer/roadmap/` carries the forward schedule: "second Thursday of February, May, August, and November" and the next major's target month. ### Connection-cost + PgBouncer source/doc map (checked 2026-08-27, REL_16_STABLE, PgBouncer 1.25.2, pgx v5)
**PG process model**: docs/16/tutorial-arch.html "To achieve this it starts ("forks") a new process for each connection"; docs/16/connect-estab.html "PostgreSQL implements a "process per user" client/server model… every client process connects to exactly one backend process"; docs/16/kernel-resources.html §19.4.3 "The PostgreSQL server uses one process per connection" and §19.4.1 "one semaphore per allowed connection". Fork path: `postmaster.c` header "When a request message is received, we now fork() immediately", `BackendStartup()` → `fork_process()` (`src/backend/postmaster/fork_process.c`, a thin `sigprocmask`+`fork()` wrapper — COW, so fork itself is NOT the dominant cost). **Connect/disconnect is the serialized part**: `procarray.c:ProcArrayAdd()`/`ProcArrayRemove()` take **ProcArrayLock AND XidGenLock both LW_EXCLUSIVE** plus 4 `memmove`s over the dense arrays; ProcArrayAdd emits `ERRCODE_TOO_MANY_CONNECTIONS` "sorry, too many clients already" (also `proc.c:InitProcess()` when the PGPROC freelist is empty). **Snapshot cost is dated pre-PG14 lore — correct it**: `procarray.c:GetSnapshotData()` takes ProcArrayLock only LW_SHARED, `GetSnapshotDataReuse()` can skip the scan entirely via the xact-completion counter, and the loop `for (pgxactoff = 0; pgxactoff < numProcs; pgxactoff++)` skips an idle backend with one dense-array read + `if (likely(xid == InvalidTransactionId)) continue;`. So O(connections) in form, tiny constant for idle ones — PG 14 item E.25.3.1.5 "Improve the speed of computing MVCC visibility snapshots on systems with many CPUs and high session counts (Andres Freund)… This also improves performance when there are many idle sessions" (commits 1f51c17c68d, 941697c3c1a, 5788e258bb2, 73487a60fc1, 623a9ba79bb, dc7420c2c). **The still-O(backends)-under-exclusive-LWLock path**: `sinvaladt.c:SICleanupQueue()` takes SInvalWriteLock + **SInvalReadLock LW_EXCLUSIVE** ("Lock out all writers and readers") then loops `for (i = 0; i < segP->lastBackend; i++)`. Shared mem per conn: `proc.c:ProcGlobalShmemSize()` = TotalProcs × (sizeof(PGPROC) + xids + subxidStates + statusFlags); `FP_LOCK_SLOTS_PER_BACKEND 16` (`proc.h`). **Per-backend private memory — no citable headline figure exists.** Floor is measured in Andres Freund's msg-id `20231012170105.zhybmddizcm4kmii@awork3.anarazel.de` (2023-10-12, "Separate memory contexts for relcache and catcache"): fresh backend on a trivial schema ≈ CatCache 370 kB + RelCache 244 kB + index info 104 kB ≈ **under 1 MB**; grows with distinct relations/plans touched and never shrinks. Multipliers are docs-citable: work_mem 4MB default × hash_mem_multiplier 2.0, "several sort and hash operations at the same time… several running sessions could be doing such operations concurrently"; temp_buffers 8MB default. Measure per-instance with `pg_backend_memory_contexts` (docs/16/view-pg-backend-memory-contexts.html, superuser/pg_read_all_stats). **Wiki sizing formula** `((core_count * 2) + effective_spindle_count)` — wiki.postgresql.org/wiki/Number_Of_Database_Connections, but **last edited 14 March 2014, written against PG 9.2** — always date-flag it. Same page carries the deliberate "no built-in pooler" rationale and the O(N^2)/O(N*log(N)) internal-structures claim. **PgBouncer** (canonical spelling, capital P + B, per pgbouncer.org): pgbouncer.org/features.html carries the verbatim pool-mode definitions and the SQL-feature-map table (transaction pooling: SET/RESET **Never**, LISTEN **Never** but NOTIFY **Yes**, WITH HOLD CURSOR Never / WITHOUT HOLD Yes, PREPARE/DEALLOCATE Never but protocol-level prepared plans Yes, PRESERVE/DELETE ROWS temp tables Never but ON COMMIT DROP Yes, LOAD Never, **session-level** advisory locks Never); "Low memory requirements (2 kB per connection by default)". Single-threaded: config.html so_reuseport "(PgBouncer is single-threaded and uses one CPU core per instance.)"; loop is libevent — `src/main.c:main_loop_once()` → `event_base_loop(pgb_event_base, EVLOOP_ONCE)`, README.md requires "Libevent 2.0+". Protocol-level named prepared statements added in **1.21.0 (2023-10-16, "The one with prepared statements")**, default max_prepared_statements **0 (off) until 1.24.0 (2025-01-10)** which set it to 200 — check the installed version before assuming pgx works. Defaults: pool_mode session, default_pool_size 20, max_client_conn 100, min_pool_size 0, reserve_pool_size 0, query_wait_timeout 120.0s, pkt_buf 4096. Queue depth is observable via `SHOW POOLS` `cl_waiting`/`maxwait`. **pgx v5** default is `QueryExecModeCacheStatement` (`conn.go:192`, named protocol-level prepared statements); `doc.go` §PgBouncer names the fallbacks: `QueryExecModeExec` (preferred), also CacheDescribe and SimpleProtocol, and explicitly **"Do not use QueryExecModeDescribeExec with transaction pooling"**. Registry gap: pgbouncer.org, github.com/pgbouncer/pgbouncer, and github.com/jackc/pgx are NOT in TRUSTED_SOURCES.md.

### pg_dump vs PITR — source map + doc page map for backup-strategy questions (checked 2026-08-27, REL_16_STABLE)
The recurring "dumps are not PITR" question. **pg_dump snapshot**: `src/bin/pg_dump/pg_dump.c:setup_connection()` — `BEGIN` then `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ, READ ONLY`; only `--serializable-deferrable` switches to `SERIALIZABLE, READ ONLY, DEFERRABLE` (REL_16 ~L1294-1311, code comment calls the mixed-mode worker handling "a kluge, but safe for back-patching"). Parallel dump consistency via `get_synchronized_snapshot()` → `pg_catalog.pg_export_snapshot()` + `SET TRANSACTION SNAPSHOT` (~L1325, L1357). Snapshot timing precision: REPEATABLE READ takes it at "the start of the first non-transaction-control statement", NOT at `BEGIN` (docs/16/transaction-iso.html) — so RPO is measured from dump **start**, not completion. **Data path**: `dumpTableData_copy()` (~L2118) emits plain `COPY %s %s TO stdout;`, only using `COPY (SELECT …) TO` for foreign tables or `--table-and-children`/filter conditions (~L2152-2177) → full seq scan of every heap. Indexes are dumped as DDL text only — `dumpIndex()` (~L16520) prints `indxinfo->indexdef` from `pg_catalog.pg_get_indexdef()` (~L7143), so a dump never reads index pages (index corruption invisible; amcheck covers that). Checksum verification on the read path: `bufmgr.c` ~L1137 `PageIsVerifiedExtended()` → `bufpage.c:PageIsVerifiedExtended()` (~L88) `pg_checksum_page()`, `ERRCODE_DATA_CORRUPTED`; `ignore_checksum_failure` default **false** (`guc_tables.c` ~L1110-1121, PGC_SUSET, GUC_NOT_IN_SAMPLE). **Cache-pollution myth**: a dump does NOT trash shared buffers — `heapam.c:initscan()` ~L330 `GetAccessStrategy(BAS_BULKREAD)`, ring = **256 kB** (`freelist.c` ~L557-559; BAS_BULKWRITE 16 MB, BAS_VACUUM 256 kB). Real load costs are I/O volume, `LOCK TABLE … IN ACCESS SHARE MODE` on every dumped table (`pg_dump.c` ~L6852-6874), and the long-lived xmin horizon (`procarray.c:ComputeXidHorizons()` ~L1731, `h->data_oldest_nonremovable` folded from every running backend's xmin ~L1858) blocking dead-tuple removal cluster-wide. **Doc page map**: backup-dump.html = "internally consistent … snapshot of the database at the time pg_dump began running", cross-major-version + cross-architecture portability, "file-level backups and continuous archiving are both extremely server-version-specific"; continuous-archiving.html = base backup + WAL replay, "restore the database to its state at any time since your base backup was taken", "can only support restoration of an entire database cluster, not a subset"; backup-file.html = cluster-only, `pg_xact/*` argument; app-pgbasebackup.html = "Backups are always taken of the entire database cluster; it is not possible to back up individual databases or database objects"; runtime-config-wal.html = `wal_level` (default `replica`; `minimal` "does not contain sufficient information for point-in-time recovery"), `archive_mode`/`archive_command`/`archive_library`, and the `recovery_target_{time,lsn,xid,name}`/`_inclusive`/`_timeline`/`_action` set; populate.html = restore cost is index + FK rebuild, pg_restore `-j`; app-pgrestore.html = `-j` "Only the custom and directory archive formats", selective `-t`/`-n`/`-l`/`-L`. **PG 16 pg_dump compression**: gzip (default), lz4, zstd, none — release-16.html E.16.3.9.2 "Add LZ4 and Zstandard compression to pg_dump", plus `--compress=gzip:5` method:level syntax. Out of registry (needs AWS docs): RDS `BackupRetentionPeriod`, whether RDS enables data checksums, RDS not exposing `archive_command`; also `pg_back` (github.com/orgrim/pg_back) is a third-party pg_dump/pg_dumpall wrapper — inherits pg_dump semantics but is not a trusted source. **Base had NO backup/PITR article as of 2026-08-27** (INDEX.md still "No articles yet").

### Materialized-view refresh + no-query-rewrite source map (checked 2026-07-20, REL_17/REL_18 identical)
All refresh logic in `src/backend/commands/matview.c`. **Lock**: `matview.c:128` `lockmode = stmt->concurrent ? ExclusiveLock : AccessExclusiveLock;` (identical 17/18) — plain REFRESH = AccessExclusiveLock (blocks SELECT); CONCURRENTLY = ExclusiveLock (SELECT/AccessShareLock still allowed). **Always a full recompute**: both paths call `refresh_matview_datafill(dest, dataQuery,…)`; non-concurrent builds a new heap via `make_new_heap()` then swaps relfilenumbers (RefreshMatViewByOid header comment ~L143), concurrent builds full new data in a TEMP table then `refresh_by_match_merge()`. `refresh_by_match_merge()` header (~L595-611): FULL-JOIN diff into a temp table holding old TID + new ROW, then set-based DELETE+INSERT, all under ExclusiveLock — comment says it deliberately "prohibit not only concurrent REFRESH operations, but also incremental maintenance." **CONCURRENTLY unique-index gate**: `matview.c:248-276`, iterates `RelationGetIndexList` for a usable unique index, errhint "Create a unique index with no WHERE clause on one or more columns of the materialized view." **No incremental/fast refresh + on-demand-only, proven at the grammar**: `src/backend/parser/gram.y` `RefreshMatViewStmt: REFRESH MATERIALIZED VIEW opt_concurrently qualified_name opt_with_data` — only CONCURRENTLY + WITH [NO] DATA, no INCREMENTAL/FAST/ON COMMIT (identical REL_17 L4811 / REL_18 L4925). **No automatic query rewrite** (planner never substitutes a matview for base tables): `src/backend/rewrite/rewriteHandler.c` ~L2091-2101 "Always ignore RIR rules for materialized views referenced in queries" + `if (rte->relkind == RELKIND_MATVIEW) continue;` (matview read as a physical relation; its stored `_RETURN` rule is used only to populate). Doc confirmations: docs/18/rules-materializedviews.html "the data is returned directly from the materialized view, like from a table; the rule is only used for populating"; docs/18/sql-refreshmaterializedview.html "completely replaces the contents", "Even with this option only one REFRESH at a time may run", plain refresh "could block other connections which are trying to read". **Base had NO materialized-view article as of 2026-07-20** (INDEX empty) — Oracle comparison is outside trusted sources 1-4 (PG-only).

### Post-upgrade ANALYZE of partitioned parents — method matters (checked 2026-06-25, REL_17/REL_18)
Whole-DB ANALYZE coverage of partitioned PARENTS (relkind 'p') splits by method. Bare `ANALYZE;` (no list) DOES include parents: `get_all_vacuum_rels()` collects RELKIND_RELATION+RELKIND_MATVIEW+RELKIND_PARTITIONED_TABLE (`src/backend/commands/vacuum.c` ~L1076-1078, both branches). But `vacuumdb --analyze-only/--all/--analyze-in-stages` WITHOUT `-t` does NOT: its client-side catalog query filters `relkind = ANY(array[RELKIND_RELATION, RELKIND_MATVIEW])` only — `src/bin/scripts/vacuumdb.c` (REL_17 ~L725, REL_18 ~L916), identical across versions, unconditional w.r.t. analyze mode. So the standard post-upgrade `vacuumdb --all --analyze-*` skips partitioned parents; fix with explicit `-t parent` or a bare `ANALYZE`. pg_upgrade stats transfer: PG≤17 carries NONE (`check.c` output_completion_banner "Optimizer statistics are not transferred"); PG 18 carries MOST via pg_dump `--statistics` (`pg_dump.c` getRelationStatistics covers RELKIND_PARTITIONED_TABLE @ ~L6957, dumpRelationStats emits both inherited=false/true rows via pg_restore_attribute_stats) but NOT extended stats (CREATE STATISTICS) and NOT cumulative stats — release notes E.5.3.7.2 "Extended statistics are not preserved"; docs/18/pgupgrade.html "transfer most optimizer statistics… not all… such as those created explicitly with CREATE STATISTICS". autovacuum NEVER processes partitioned parents: `do_autovacuum()` enumerates only RELKIND_RELATION/RELKIND_MATVIEW (`src/backend/postmaster/autovacuum.c` ~L2004-2005). ANALYZE docs Notes (17 & 18) state autovacuum doesn't process partitioned tables and child changes don't count toward the parent threshold. PG18 vacuumdb `--missing-stats-only` has inheritance branches (stainherit/stxdinherit) but they only evaluate relations already past the relkind filter, so they can't reach a relkind-'p' parent absent `-t`.

### pg_stat_statements_reset() — definition and privilege model (checked 2026-06-18, master/PG19-dev)
Function SQL definitions live in `contrib/pg_stat_statements/pg_stat_statements--*.sql` (upgrade scripts); C entry points `pg_stat_statements_reset` / `_1_7` / `_1_11` and the shared worker `entry_reset()` in `pg_stat_statements.c`. No-arg / all-zero call resets every entry and, when all entries are gone, resets the global `pg_stat_statements_info` counters (`entry_reset()` "Reset all entries" branch + `pgss->stats.stats_reset`). The privilege restriction is purely a SQL-level `REVOKE ALL ... FROM PUBLIC` on each signature — `entry_reset()` itself has NO role check (the role check in `pg_stat_statements_internal` guards the *view*, not reset). So default = superuser only; grantable via `GRANT EXECUTE`. Signature timeline: no-arg in 1.0; `(userid,dbid,queryid)` in 1.7 (PG 13); `minmax_only` 4th arg + `returns timestamptz` in 1.11 (PG 17, script `1.10--1.11.sql`). Brief window in 1.5 only, EXECUTE was granted to `pg_read_all_stats`, then revoked again in 1.6.
