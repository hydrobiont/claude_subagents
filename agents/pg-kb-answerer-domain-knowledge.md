### Post-upgrade ANALYZE of partitioned parents — method matters (checked 2026-06-25, REL_17/REL_18)
Whole-DB ANALYZE coverage of partitioned PARENTS (relkind 'p') splits by method. Bare `ANALYZE;` (no list) DOES include parents: `get_all_vacuum_rels()` collects RELKIND_RELATION+RELKIND_MATVIEW+RELKIND_PARTITIONED_TABLE (`src/backend/commands/vacuum.c` ~L1076-1078, both branches). But `vacuumdb --analyze-only/--all/--analyze-in-stages` WITHOUT `-t` does NOT: its client-side catalog query filters `relkind = ANY(array[RELKIND_RELATION, RELKIND_MATVIEW])` only — `src/bin/scripts/vacuumdb.c` (REL_17 ~L725, REL_18 ~L916), identical across versions, unconditional w.r.t. analyze mode. So the standard post-upgrade `vacuumdb --all --analyze-*` skips partitioned parents; fix with explicit `-t parent` or a bare `ANALYZE`. pg_upgrade stats transfer: PG≤17 carries NONE (`check.c` output_completion_banner "Optimizer statistics are not transferred"); PG 18 carries MOST via pg_dump `--statistics` (`pg_dump.c` getRelationStatistics covers RELKIND_PARTITIONED_TABLE @ ~L6957, dumpRelationStats emits both inherited=false/true rows via pg_restore_attribute_stats) but NOT extended stats (CREATE STATISTICS) and NOT cumulative stats — release notes E.5.3.7.2 "Extended statistics are not preserved"; docs/18/pgupgrade.html "transfer most optimizer statistics… not all… such as those created explicitly with CREATE STATISTICS". autovacuum NEVER processes partitioned parents: `do_autovacuum()` enumerates only RELKIND_RELATION/RELKIND_MATVIEW (`src/backend/postmaster/autovacuum.c` ~L2004-2005). ANALYZE docs Notes (17 & 18) state autovacuum doesn't process partitioned tables and child changes don't count toward the parent threshold. PG18 vacuumdb `--missing-stats-only` has inheritance branches (stainherit/stxdinherit) but they only evaluate relations already past the relkind filter, so they can't reach a relkind-'p' parent absent `-t`.

### pg_stat_statements_reset() — definition and privilege model (checked 2026-06-18, master/PG19-dev)
Function SQL definitions live in `contrib/pg_stat_statements/pg_stat_statements--*.sql` (upgrade scripts); C entry points `pg_stat_statements_reset` / `_1_7` / `_1_11` and the shared worker `entry_reset()` in `pg_stat_statements.c`. No-arg / all-zero call resets every entry and, when all entries are gone, resets the global `pg_stat_statements_info` counters (`entry_reset()` "Reset all entries" branch + `pgss->stats.stats_reset`). The privilege restriction is purely a SQL-level `REVOKE ALL ... FROM PUBLIC` on each signature — `entry_reset()` itself has NO role check (the role check in `pg_stat_statements_internal` guards the *view*, not reset). So default = superuser only; grantable via `GRANT EXECUTE`. Signature timeline: no-arg in 1.0; `(userid,dbid,queryid)` in 1.7 (PG 13); `minmax_only` 4th arg + `returns timestamptz` in 1.11 (PG 17, script `1.10--1.11.sql`). Brief window in 1.5 only, EXECUTE was granted to `pg_read_all_stats`, then revoked again in 1.6.
