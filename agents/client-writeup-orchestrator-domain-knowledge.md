### The QA pair
- **Fact pass:** `training-fact-checker` agent — charter says training slides, so re-scope per invocation (target file, "client write-up", explicit verification sources). Returns per-claim verdicts, never edits. Fallback: `general-purpose` seeded with the verdict-table methodology.
- **Style pass:** `tighten-prose` skill at `~/.claude/skills/tighten-prose/SKILL.md` — per-word deletion test; never cuts identifiers, version qualifiers, negations, numbers, command output, or deliberate voice.

### Downstream compile
`client-report-builder` turns a finished report into branded HTML + PDF via `~/.dataegret/markdown-converter/converter.sh` — it requires the standard YAML frontmatter. Hand off only when the user declares the write-up final.

## Workflow, structure & reference — JN-1 architecture workshop (2026-08-28)

Durable facts from drafting the JoyNext RDS architecture workshop (`joynext_internal/2026/JN-1/joynext_architecture_workshop_aug_2026.md`); the style patterns from the same engagement are in the entry below.

- **Workshop solution-strategy shape.** Expanded sections are `## <topic>` in the order of the numbered overview at the top of Solution strategy, each with `### Current observations` → topic subsections → `### Recommendations` (mirroring the user's own Retention and archiving section). Recommendations earn trust through cross-links to the client's discovery facts and stated constraints — e.g. blue/green blocked by the two no-PK tables found in Schema design; backup-file-outside-AWS requirement satisfied by keeping `pg_back` dumps. Every recommendation between alternatives closes with a revisit condition.
- **Baseline sequencing pattern.** When the only load is synthetic and it hits a hard ceiling (here: the RDS connection limit), a pgCluu/pgBadger baseline measures the ceiling, not the database. Order: remove the known first bottleneck (connection pooling), then baseline, then everything that needs the baseline (Aurora sizing, performance review). The user rewired two sections around this rationale.
- **pgCluu/pgBadger on managed AWS (RDS/Aurora) — canonical instructions** live at `pricemoov/dataegret_pricemoov_report_v1.1/pgcluu_pgbadger_aurora.md`: collector on an external host (no OS access), `--disable-sar --no-sysinfo`, and the logging parameter set — `log_connections=1`, `log_disconnections=1`, `log_lock_waits=1`, `log_temp_files=0`, `track_io_timing=1`, `log_min_duration_statement=1000` standing / `0` only for short full-trace windows, then revert. `log_statement` stays `none`.
- **pg-utils daily slow-query report.** The report Data Egret recommends is `sql/global_reports/query_stat_total.sql` in github.com/dataegret/pg-utils (per-version variants; `query_stat_total_16.sql` is a symlink to the `_13` variant — raw fetch of a symlink returns the target path as content). Verified by live run (PG 16.11, 2026-08-28): prints a header (total time, I/O share, query counts) then a ranked top by total execution time with share, CPU-vs-I/O split, calls, avg time, rows, user, db, normalized query. House pattern for clients: daily cron on a small VM/pod → store report (S3/email) → `pg_stat_statements_reset()` so each report covers one day; a top that changes after a release points at the release.
- **AWS pricing verification method.** aws.amazon.com pricing pages are JS-rendered and return no numbers to WebFetch. The reliable source is the Price List API offer file, e.g. `https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonRDS/current/eu-central-1/index.json` (fetched by a general-purpose subagent). Always label prices in reports with region + on-demand + as-of month. Some AWS docs pages also fetch empty (e.g. the backup-window page); fallback is WebSearch with exact quoted doc phrases.
- **pg-kb-answerer groundwork exists** (in its own domain knowledge, 2026-08-27/28) for: pg_dump-vs-PITR semantics, connection cost/PgBouncer/pgx exec modes, PostgreSQL release lifecycle + 18.x anomalies. Ask it before re-deriving any of these.

## User's editing patterns — from the JN-1 manual-correction diff (2026-08-28)

Source: user's hand edits to `joynext_internal/2026/JN-1/joynext_architecture_workshop_aug_2026.md` (Connection pooling + High availability sections) over the AI draft. All facts and structure survived; corrections are wording register and reader-service. Apply alongside the BI-01 list below:

1. **Link PostgreSQL objects a customer would look up.** Bare `` `pg_backend_memory_contexts` `` became a markdown link to the official docs — and to `/docs/current/`, not a version-pinned URL, in client-facing text. First mention of a system view/GUC/tool the customer may want to read up on gets an inline official-docs link.
2. **No rhetorical segues — flat introductions.** "A connection pooler exploits exactly this:" → "A connection pooler works the following way:". Extends the no-metaphors rule to clever connective phrasing: introduce a mechanism by announcing the description, not by a callback to the previous paragraph.
3. **Avoid reliability jargon where a plain word works.** "remove the connection-exhaustion failure mode" → "…failure problem". "Failure mode" reads as engineering-speak to him; prefer "problem"/"risk".
4. **A specific verification instruction appears once, at the actionable spot.** The RDS Proxy option bullet's "confirmed with the existing load test" was generalized to "confirmed with a test", while the Suggested path kept the full "validate with the existing load test, watching the pinning metric". Don't repeat the concrete test/metric prescription in every mention; earlier mentions stay generic.
5. **Never claim "no application change" for anything that moves the endpoint.** "a Terraform-level change with no application change" (RDS Proxy) → "easy to deploy with Terraform". Pointing the application at a proxy endpoint IS an application-visible change; state the deployment ease without the false "no change" claim.
6. **Close alternative-picking recommendations with an explicit revisit condition.** He appended: "If the application in the future evolves to a state when more features from PgBouncer are required, this conclusion can be reconsidered." A recommendation between alternatives is valid-for-now, and the report should say under what condition it gets re-opened.

## User's editing patterns — from the BI-01 manual-correction diff (2026-07-17)

Source: `boehringer_ingelheim_internal` commits `54dd468` (AI draft) → `620f064` (user's corrections). All verified facts, links, and section structure survived; every correction is register, layout, or completeness. Apply these when drafting:

1. **No metaphors, no idioms — literal consequence statements.** "PostgreSQL-side blast radius" → "Source PostgreSQL database is at risk."; "no failover" → "no HA" (the domain acronym, not a description). If a phrase paints a picture instead of naming the failure, replace it.
2. **Three or more parallel items = a bullet list, never semicolon prose.** Packed evaluation criteria became "Evaluation criteria:" + bullets; an inline "(+) … (−) …" paragraph became two bullets with bold `**(+)**` / `**(−)**` markers. Preserve the user's conspect notation ((+)/(−)) as visible list markers.
3. **Recommendations end bare.** The decision sentence only ("Kafka Connect with the Debezium PostgreSQL connector, deployed and managed through CFK on OpenShift."); the justification tail was cut — rationale lives in the assessment above, not appended to the verdict.
4. **Operational framing beats abstract framing.** "the problems are properties of the standalone runtime" → "the problems are in scope of every day operations of the standalone runtime". Say what operations will face, not what something "is".
5. **State the risk, not the analytic process.** "the TPS estimation feeds this sizing directly" → "the TPS estimation can be an issue". Name the potential problem; drop process narration.
6. **Every fault-tolerance claim resting on customer infrastructure gets an open question + cross-link.** "offsets stored in replicated Kafka topics" implicitly assumed the customer's Kafka is HA — the user added "(See question about Kafka availability in open questions.)" and a new open item "Are the connectors and topics replicated?". Audit drafts for unstated assumptions about the customer's platform.
7. **Aggregate Data Egret experience is welcome; engagement-specific detail is not.** His pattern: "We at Data Egret experienced this problem with the majority of our customers who use standalone Debezium. There are also publicly available stories of such problems." — first-person-plural aggregate, then "publicly available stories" as the bridge into citations. Never a single identifiable engagement.
8. **Open-items hygiene:** items covered by the Solution strategy are deleted (per the template comment); related sub-questions merge into one bullet, optionally with a first-person working note ("I assume it can, but what are official recommendations about number and size of tables?"); every question ends with "?". Commercial notes ("Data Egret can help with creation as a separate consulting engagement") are the user's to add — keep them verbatim when reshaping.
9. **Process/handbook sections name the concrete stack constraints** — he added "we need to keep in mind Patroni and synchronous replication" to the handbook intro. Tie generic process items to the customer's actual cluster properties.
10. **Spelling: corrected "Standardised" → "Standardized" (US -ize)** — but left "re-initialised", "Synchronisation", "data centres" untouched, so the document is mixed; treat -ize as the preferred direction and confirm with the user before normalising wholesale.
11. **The user's own dictated text carries artifacts** ("high-valuability" = high-availability, "I have a baseline" = "to have a baseline", "team school main session" = likely "Teams call"). Decode the intended phrase from context; flag the interpretation instead of copying the artifact forward.
12. **Label every claim with the correct layer — and verify what ships, not only what's documented.** A BI-01 bullet headed "**Avro.**" implied a serialization-format gap between Debezium Server and Kafka Connect; the user caught the conflation (2026-07-17). Verified reality: both deployments emit Avro; the difference is the bundled schema-registry client (Debezium Server ships Apicurio-only — zero `io.confluent` JARs in the server image; its engine silently defaults to Confluent's `AvroConverter` class when no Apicurio URL is set, producing class-not-found on the stock distribution; Confluent's cp-server-connect images ship the Confluent Avro converter natively; Apicurio's ccompat API is one-directional — Confluent clients → Apicurio server). When summarizing research into report bullets, keep format / registry / wire-format / client-library claims in their own layers, and prefer image/artifact inspection over docs inference for "what's included" claims.
