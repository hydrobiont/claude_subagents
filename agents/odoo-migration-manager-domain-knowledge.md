### odoo.sh staging + neutralization + inbound reachability — the documented contract (19.0 docs, researched 2026-08-13)
Cited answers for any design that wants to rehearse an external integration on staging. **Staging DB** = *"neutralized duplicates of the production database"*; **auto-deleted after one month** ("To use the branch again, you must rebuild it"); **not automatically backed up** (a production backup can be restored into it; manual staging backups allowed); dev DBs last ~3 days. ⚠ **The 19.0 docs contradict themselves on the push default** — `builds.html`: *"Each time you push a new revision to a staging branch, the resulting build uses a fresh copy of the production database"*; `branches.html`: *"By default, a development branch creates a new build and a staging branch **updates** the previous build"* unless the branch's *Behavior upon new commits* is set to "New build". Treat the per-branch setting as authoritative and read it off the dashboard. **Neutralization** (`administration/neutralized_database.html`, explicitly *non-exhaustive*): scheduled actions, **outgoing emails**, bank synchronization, **payment providers**, delivery methods, IAP tokens, website indexing; red banner. **Outgoing mail is intercepted by a mail catcher with a UI — the branch's "Mails" tab** (*"available for development and staging branches. Emails from the production database are actually sent and are not intercepted"*); per-build it is the "Outgoing e-mails" item under More Actions. **Payment providers on staging: three official sources disagree** — `neutralized_database.html` says deactivated, odoo.sh `branches.html` says *"put into test mode"*, the odoo.sh FAQ says *"all built-in payment processor credentials are removed (Stripe, Paypal, …)"*; source `addons/payment/data/neutralize.sql` reconciles as `state='disabled'` unless already `test`. **⇒ Design on the assumption a Stripe round trip is NOT exercisable on staging**, and note the payment-providers doc warns *"We recommend using the test mode on a duplicate or a test database to avoid potential issues with invoice numbering"* — which, with the undeletable German audit trail, rules out test-mode rehearsal on prod. **★ Inbound HTTPS to a staging build IS public**: builds are served on `*.dev.odoo.com` port 443, the FAQ states *"Each Odoo build comes with an XML-RPC interface… the database URL (eg: mydatabase.dev.odoo.com); the port number is 443"* and *"if you require communication with a third-party system… you will need to establish the integration at the HTTP layer"*; **no auth gate, IP allowlist or basic-auth in front of a build is documented** (the `Allow public access` setting governs the odoo.sh *builds page*, not the build's HTTP endpoint). Documented limits are resource-based: staging/dev builds are *"restricted to a single worker"* with a *"HTTP rate limited"* metric — expect throttling. **A custom domain can be attached to any branch type** (*"for all branch types"*, Let's Encrypt within the hour, bare domains refused) → the documented way to get a staging hostname that survives rebuilds. **Not documented:** the "Block access to the .odoo.com domain" setting (absent from 17.0/18.0/19.0 `settings.html` and the RST sources — our root-cause finding is empirical only), a formal build-URL template, incoming-mail neutralization, expiry/registration effects. **★ Outbound webhook server actions ARE neutralized** (source `odoo/addons/base/data/neutralize.sql`: `UPDATE ir_act_server SET webhook_url='neutralization - disable webhook' WHERE state='webhook'`) — an Odoo→WordPress push silently no-ops on staging; inbound custom controllers are untouched. **There is NO odoo.sh platform API** — FAQ verbatim: *"If you are looking for an API to interact with the Odoo.sh platform (eg: creating a new project, new branches or requesting a rebuild), this is not planned to be developed for now"*; the documented control plane is GitHub pushes + commit statuses, so branch/build inventory must be read from the dashboard UI. Env var `ODOO_STAGE` (`production|staging|dev`) is the documented in-container way for code to branch on stage.

### ★ `odoo.dataegret.com` is Cloudflare-PROXIED — a 403 there is the WAF, not Odoo; OWASP is now skipped for that host (diagnosed + fixed live 2026-08-04)
**Two hostnames serve the SAME production database.** `odoo.dataegret.com` is an orange-cloud (proxied) record in the `dataegret.com` Cloudflare zone (`d06ff7e352dbfd95b4944815d755f6fb`, plan **Pro Website**); `dataegret.odoo.com` resolves straight to odoo.sh (`207.175.22.251`) and touches no Cloudflare. `web.base.url` = `https://odoo.dataegret.com` **with `web.base.url.freeze = True`** (both verified live), so **every invite / password-reset link in outgoing mail traverses the WAF**.

**Attributing a failure.** Read the response `server:` header — `cloudflare` vs `Odoo.sh`. A Cloudflare block is `403` + a "Sorry, you have been blocked" page and **never reaches Odoo, so odoo.sh logs are silent** — do not go hunting in Odoo for it. Trap: the block page interpolates the **zone apex**, printing *"You are unable to access dataegret.com"* even when the request went to `odoo.dataegret.com`; it is almost never the WordPress site. Per-user workaround while a WAF issue is open: swap the hostname to `dataegret.odoo.com`, keeping the token query string — same DB, no proxy.

**What was wrong (2026-08-04).** The **OWASP Core Ruleset** ran at Cloudflare defaults (score threshold 40, **no overrides**) and was scoring ordinary Odoo traffic over the line: `GET /web/login/totp` (the 2FA page — score exactly 40, blocked a real internal user two seconds after he set his password via an invite, which is how this surfaced), `POST /report/download` (45), `POST /website/form/helpdesk.ticket` (89), and **any POST body containing SQL** — fatal for a PostgreSQL consultancy whose customers paste queries into helpdesk tickets. Realistic passwords, `${}`, `<abc>`, umlauts and long bodies never tripped it; the password was never the cause.

**Fix in place.** Managed-phase entrypoint ruleset `1d994ae8beb241c4bd895e0b1684f420`, rule **1** = `skip` → `action_parameters.rulesets = ["4814384a9e5d4991b9815dcfc25d2f1f"]` (OWASP) where `http.host eq "odoo.dataegret.com"`. **The skip must precede the execute rules** or it silently no-ops. The Cloudflare Managed Ruleset `efb7b8c949ac4650a09736fc376e9aee` is deliberately **KEPT** on that host — it still blocks `/.git/*` scanners and query-string SQLi (both re-verified after the change). Verified A/B, same payload same moment: SQL-body POST → apex **403**, Odoo host reaches the origin. Owner of that zone is the `de-website-manager` agent; its DK carries a matching do-not-remove note.

**Reading the evidence.** Security Events = GraphQL `firewallEventsAdaptive` (field is `clientRequestHTTPMethodName`, not `clientRequestMethod`). **Retention on Pro is 24 hours** — pull it the same day or it is gone. ### Odoo 19 module HTTP controllers for a bot integration — auth modes + the SEAT-FREE pattern on odoo.sh (verified 19.0 source `odoo/http.py`, 2026-07-08)
`@http.route` `auth` values (docstrings, `odoo/http.py`@19.0): **`user`** (must be logged in; runs with that user's rights); **`public`** ("may or may not be authenticated; if not, executed using the shared **Public user**" — Public is FREE, NOT a billed seat); **`bearer`** ("authenticated using an Authorization header, Bearer scheme, with an API token; executed with the permissions of the corresponding user"; session-save off by default — needs a real user ⇒ a seat if internal, but a **free portal** user's key also works); **`none`** (active even with no DB; no current-user facilities). Route `type`: **`http`** (default, CSRF **on**), **`jsonrpc`** (CSRF **off** by default; `params` must be a by-name JSON object); **`json` is a DEPRECATED alias for `jsonrpc` since 19.0**. Disable CSRF with `csrf=False`. **★ Seat-free integration pattern (unlocked by odoo.sh custom modules; was impossible on Online):** a module controller `@http.route('/slackbot/ticket', type='jsonrpc', auth='public', csrf=False)` that (1) verifies an **HMAC request signature** (shared secret in `ir.config_parameter` + bot env; timestamp + `hmac.compare_digest`, Slack-style replay window — NOT a static bearer token, so a leaked log line doesn't leak the secret), then (2) does all work under **`sudo()`** with tight per-endpoint validation. Cost = **€0 marginal** (runs as the free Public user; no dedicated internal seat, no 3-month API-key rotation treadmill, no "key inherits the user's full rights / can't be scoped" problem — the endpoint IS the least-privilege surface), and there is **no bot user to accidentally land in a helpdesk round-robin pool**. Authorship: `sudo()` ⇒ `create_uid`=SUPERUSER (uid 1, OdooBot) — acceptable as a stable "came from automation" marker; stamp an explicit source/event field for per-integration provenance and use `message_post(author_id=<customer contact>)` so chatter shows the human reporter. One controller round trip replaces the ~6 paced XML-RPC calls a ticket-create needs today (latency + AUP win). Alternative when Odoo-native key management / named-principal audit is preferred over hand-rolled HMAC: `auth='bearer'` with a **free portal** technical user's key + `sudo()` inside (still seat-free; the portal record-rule fragility from the earlier eval does NOT bite here because the controller sudo()s all real work — the portal user is only an auth-token holder). Sources: `raw.githubusercontent.com/odoo/odoo/19.0/odoo/http.py` (auth-method + route-type docstrings), docs/19.0 `developer/reference/backend/http.html`, odoo.com/pricing (portal/public free; only active internal users billed). Relevance: the Slack-bot "Odoo as source of truth" redesign (2026-07-08) — this reverses the dedicated-bot-seat decision (release-plan §4 item 5) *on odoo.sh only*.

### Odoo 19 outbound webhook (server action `state='webhook'` = base_automation "Send Webhook Notification") — fire-and-forget, lossy, unsigned (verified in 19.0 source 2026-07-08)
The native way to push an event OUT of Odoo (e.g. helpdesk stage change → an external listener). Verified against `odoo/addons/base/models/ir_actions.py`@19.0 (`raw.githubusercontent.com/odoo/odoo/19.0/...`, method family `_run_action_webhook*`): the POST runs in a **postcommit hook** (fires only after the DB transaction commits; a webhook failure does **NOT** roll back the triggering write), is a **single** `requests.post(url, data=json_values, headers={'Content-Type':'application/json'}, timeout=1)` — **1-second timeout, NO retry loop, no queue, no dead-letter** — and exceptions are **swallowed to a `_logger.warning`** ("Webhook call failed / timed out"). No HMAC/signature header ⇒ **unsigned** (a consumer can only verify via a secret-in-URL). Default JSON payload = `{'_model': <model>, '_id': <record id>, '_action': '<name>(#id)'}` plus any fields added via `webhook_field_ids` (read dynamically off the record). **Net: best-effort + lossy + unsigned** — if the target is down or slow (>1 s) the event is silently dropped. So this is NOT a reliable integration bus: a consumer that must not miss events should **PULL** (paced `search_read` on `write_date > watermark`) rather than depend on this push, or add a third-party retry/queue module. Automation-rule surface (Studio / `base_automation`): triggers = Values Updated / Email Events / Timing Conditions / Custom (On create[/& edit], On deletion, On UI change) / External (INBOUND Webhook — distinct from this action); actions = Update/Create/Duplicate Record, Create Activity, Send Email/SMS/WhatsApp, Add/Remove Followers, Execute Code, **Send Webhook Notification**, Multi Actions. Sources: the 19.0 source file above; docs `applications/studio/automated_actions.html` (+ `/webhooks.html`, which documents the INBOUND webhook *trigger*, NOT this outbound *action*); odoo.com forum 297624 (retry question left unanswered ⇒ corroborates "no native retry"). Relevance: the Slack-bot two-way-sync evaluation (2026-07-08) — this lossiness is why bot-side polling beats an Odoo→bot webhook for a Socket-Mode bot with no inbound endpoint.

### Odoo 19 real-time bus = `/websocket` with SESSION-COOKIE (password) auth — NOT an API-key integration surface (verified 2026-07-08)
Odoo 16+ replaced the old `/longpolling/poll` with a real websocket at **`/websocket`** (served by a gevent worker; **odoo.sh provisions and serves it externally automatically** — it powers the web client's Discuss / live-chat / notifications). BUT it authenticates via the **session cookie** obtained from **`/web/session/authenticate`, which is password-only (browser-oriented) and does NOT accept an API key**. So an API-key bot/integration cannot cleanly "subscribe to the Odoo bus": it would have to hold a password-based session and piggyback on a web-client surface ("not a raw websocket you hook into directly"). **Consequence for integrations:** to observe Odoo changes from an external service, use **paced `search_read` polling** (e.g. `helpdesk.ticket` where `write_date > watermark`) over XML-RPC / JSON-2 with the API key — do NOT try to consume the websocket bus. Sources: docs `administration/on_premise/deploy.html` (gevent `/websocket` worker + `--proxy-mode`), `developer/reference/external_api.html` (API-key auth model), odoo.com forum 284722. Relevance: same Slack-bot evaluation — kills pattern (a)-via-bus, leaving paced polling as the clean "pull" primitive.

### Removing the "Database neutralized for testing" banner after a restore-into-production — deactivate the VIEW, not (just) the param (Data Egret, verified live 2026-07-10)
The banner is NOT gated on `database.is_neutralized` at render time. odoo.sh neutralization **activates the `web.neutralize_banner` qweb view** (whose source default is `active="False"`), and while active it injects the banner into `web.layout` unconditionally. So deleting the `database.is_neutralized` ir.config_parameter does **not** remove the banner (and `ir.config_parameter.get_param` is per-worker ormcached, so a raw unlink only clears one worker anyway). **Fix that works, zero-downtime: set `web.neutralize_banner` `active=False`** via RPC (`ir.ui.view` write) — restores the normal-DB default; view-cache invalidation propagates cross-worker; verified gone across fresh SSO sessions. Also delete the `database.is_neutralized` param so a fresh server start comes up clean. Residual: some workers may still report `is_neutralized()=true` from ormcache until the next registry reload (next build/module upgrade) — inert IF 0 outgoing mail servers + crons inactive. **★ Consequence: once the banner/neutralization is lifted, the ONLY thing preventing real outbound mail is the absence of an outgoing mail server — do NOT configure one on prod before go-live.** De-neutralizing does NOT re-activate paused crons (their `active=False` is persisted). To fully flip `is_neutralized()` everywhere (not just the banner), reload the registry: a module upgrade (`button_immediate_upgrade` on a small custom module) or a prod update-build; the odoo.sh prod branch only exposes a heavy "Branch Rebuild", so prefer the module-upgrade lever.

### odoo.sh: the "Block access to the .odoo.com domain" setting BREAKS builds — ROOT CAUSE of "Could not establish http connection to the build" (Data Egret, verified 2026-07-08)
When a **custom domain** is configured (e.g. `odoo.dataegret.com`), it is tempting to tick **Project Settings ▸ "Block access to the .odoo.com domain"**. **Do NOT** — it makes odoo.sh builds **FAIL the post-install HTTP health-check** with *"Test: Failed — Could not establish http connection to the build (see odoo.log)"*, because odoo.sh's own health probe (and each build's live URL) use the build's `*.odoo.com` / `*.dev.odoo.com` address, which the setting blocks. **Diagnostic signature** (alarming, but NOT a code/repo bug): `install.log` clean (modules load + `--stop-after-init`), `odoo.log` EMPTY (serve process never reachable/logged), **"View errors" = "Unable to find errors"**, reproducible across rebuilds, ~20s duration. **FIX = untick the checkbox** (the custom domain still serves production; you just cannot fully block `.odoo.com` or odoo.sh can't reach its own builds/health-checks). ### easyBill invoices in Odoo — the post-vs-draft legal tension, and how to represent them as non-legal copies (verified live 2026-06-30, read-only)
The user's constraint: easyBill stays the LEGAL system of record (synced to external accounting separately); Odoo must NOT become a second legal invoice set. Refined scope (user, 2026-06-30): invoices dated **≤ 31 May 2026** are easyBill's already-issued legal originals → represent as non-legal copies; **June 2026 onward is undecided → a Odoo DRAFT without payment matching is acceptable for now**. The cut line is **2026-06-01**. **The core tension (verified by Odoo architecture):** native payment reconciliation (`account.payment.register` wizard, bank-statement matching, `payment_state` transitions to in_payment/paid) operates **only on POSTED moves** — and posting assigns a journal sequence number + books to the GL, i.e. exactly the "second legal set" to avoid. **Drafts** (`state=draft`) are non-legal, don't hit the ledger, and are **excluded from every statutory report** (`account_reports`+`l10n_de_reports` are installed; VAT/EC-Sales/Tax reports read posted moves only) — but a draft **cannot** use native payment matching. So payment status on a draft can only be a stored DATA field, not a reconciled state. **Labelling fields that actually exist on `account.move` in saas-19.3** (verified `fields_get`): `ref` (char "Reference"), `narration` (html "Terms and Conditions"), `name` (char "Number"), `invoice_origin` (char "Origin"), `payment_state` (selection: not_paid/in_payment/paid/partial/reversed/blocked/invoicing_legacy), `state` (draft/posted/cancel). **NO `tag_ids`/`to_check`/`checked`/generic label many2many on account.move** (unlike res.partner) — so "tag as duplicate" must use `ref`/`narration`/a dedicated journal, or a Studio `x_studio_*` field (Custom plan, Studio installed on this trial). `has_draft_move_duplicate` exists but is a computed vendor-bill-oriented detector (=0 on all 39 our drafts) — not a usable manual flag. **payment_state CAN be written as a label on a draft** but won't reflect real reconciliation. **Recommended approach (easyBill permanent / Odoo = visibility layer): keep all ≤May invoices as DRAFTS, stamp `ref`=easyBill number + a `narration` banner "COPY of easyBill original — not a legal invoice; payment status mirrored from easyBill", and store easyBill's paid/open status either by writing `payment_state` as data or (cleaner) a Studio `x_studio_eb_payment_status` field.** Only if the user wants TRUE payment reconciliation in Odoo do you post — and then ONLY into a **dedicated isolated sale journal** (e.g. "easyBill — migrated copies") that is kept out of statutory/tax filing, with legacy numbers preserved on `name` (settable on a draft, sticks through posting). Live state at probe: **40 customer `out_invoice` (39 draft + 1 cancel), 0 posted, journal = Sales (id 8, the only sale journal), 28 dated ≤May / 12 dated ≥June**; 25 carry an easyBill number on `name`, 15 have `name=False` (Odoo placeholder "/") incl. all subscription-origin drafts; 9 drafts are subscription-generated (`invoice_origin`=S000xx, all created by uid 2 via loader scripts, NOT a cron). Anomaly to note: draft `2026-05-034-10177` (Tabby) reads `payment_state=paid`/residual 0 while still draft — a loader side effect, harmless. **The one decision only the user can make:** is Odoo EVER meant to take over legal invoicing later, or is easyBill permanent and Odoo purely visibility/CRM/helpdesk? — that flips the recommendation between "drafts forever + data-only payment status" and "build a clean isolated-journal posting path now."

Settings ▸ Technical ▸ Scheduled Actions is visible and you can toggle existing crons, but authoring a new cron whose body is your own Python is blocked on SaaS — that needs a real module on odoo.sh/on-prem. **Studio's "Timing Conditions" trigger is NOT a substitute for a monthly cron**: it fires per-record relative to a date field on that record (e.g. "30 days after `date_x`"), so it cannot natively express "on the 1st of every month, scan ALL active subscriptions, sum each one's billable timesheets, draft an overage line." A monthly-reset usage meter therefore = **Tier 3 (odoo.sh)** unless approximated by per-record date-triggered rules (fragile). Our current overage logic (`scripts/odoo_overage_invoice.py`) runs EXTERNALLY via XML-RPC and stays external on Online — it can only move *in-platform* (as an `ir.cron`) on odoo.sh.
- **Verdict shorthand: "You only need odoo.sh IF you want the monthly included-hours meter / overage job (and per-customer allowance fields) to live INSIDE Odoo as a real cron + DB columns instead of an external script + CSV."** Everything else in the lifecycle (CRM intake/stages, won→quote→subscription, subscription auto-invoice, project/task on order, timesheet capture, Helpdesk intake/assign/SLA, Studio custom field for terms) is achievable on **Online + Custom + Studio**. odoo.sh trade-off: gains shell/Postgres/code + staging branches, but YOU own module maintenance across Odoo's rolling upgrades and it's a heavier hosting tier — only worth it for the one genuine code need plus any future custom modules.

### EU cross-border e-invoicing — ZUGFeRD/Factur-X vs Peppol (researched 2026-06-10)

For a **German supplier emailing B2B invoices to EU customers** (not on the Peppol network): **ZUGFeRD 2.1 ≡ Factur-X 1.0** — a **PDF/A-3 with embedded UN/CEFACT CII XML conformant to EN 16931** (use the **EN16931/COMFORT profile or higher**, NOT MINIMUM/BASIC-WL). It is human- AND machine-readable in one file and **emailable with no Access Point**. **Peppol BIS Billing 3.0** is pure UBL XML (also EN16931) with **no human-readable PDF**, designed for the Peppol 4-corner network (needs a Peppol ID + Access Point) — not ad-hoc email. Decisive point: **a German supplier's invoices to other-EU customers are cross-border intra-EU B2B, which is OUT OF SCOPE of every country's domestic B2B e-invoicing mandate** (those bind only suppliers *established* in that country) — so an emailed EN16931 hybrid is compliant to all. Country notes among DE's customers: **France** — Factur-X is its flagship (so ZUGFeRD/Factur-X is a *plus*; French-established clients route via PDPs/Peppol, irrelevant to a foreign supplier); **Belgium** (mandate 1 Jan 2026) and **Estonia** (buyer-choice since 1 Jul 2025) default to **Peppol delivery** — a customer there may *prefer* Peppol but cannot require it cross-border; **Cyprus/Lithuania/Latvia/Malta** — no B2B mandate in force (2026). "Peppol = Belgian" is wrong — Peppol is global (~46 member countries, ~2.5M participants in 111 countries), though Belgium's mandate does default to it. In Odoo this is `res.partner.invoice_edi_format`: `zugferd` (Germany), `facturx` (France, identical CII), `xrechnung` (German pure-XML, for B2G/recipients that demand it), `ubl_bis3` (Peppol). Sources: docs.peppol.eu/poacc/billing/3.0, pdflib ZUGFeRD/Factur-X KB, EC eInvoicing country pages (France/Belgium/Estonia/Cyprus/Lithuania), Wikipedia/PEPPOL.

### saas-19.3 ORM `Domain` parser is strict — empty `[]` and `"&"`-prefixed *list* leaves break over XML-RPC (verified 2026-06-10)

Odoo 19's rewritten `odoo/orm/domains.py` validates search domains harder than older Odoo, and two long-standing idioms now raise via XML-RPC `execute_kw`: (1) an **empty domain `[]`** → `ValueError: Domain() invalid item in domain: []` (so `search_count(model, [[]])` fails) — pass a truthy catch-all like `[("id", ">", 0)]` instead of `[]` for "all records"; (2) the **explicit polish-notation `"&"` prefix with bracketed *list* leaves**, e.g. `[["&", ["a","=",1], ["b","=",2]]]`, → `TypeError: unhashable type: 'list'` (the parser tries to hash a leaf as an operator). Fix: use **implicit-AND with tuple leaves** — `[("a","=",1),("b","=",2)]`. Single-leaf domains also want a tuple: `[("move_type","=","out_invoice")]`, not `[["move_type","=","out_invoice"]]`. NB the earlier `scripts/odoo_set_is_company.py` uses the old `"&"`+list form and the `[[...]][0]` unwrap trick — it ran on the partner `search_count`/`write` there, but the same construct now fails on `search_count`/`search_read` against `account.*` and `ir.model.data`; prefer the tuple/implicit-AND form in all new scripts. Read-only probe template using the correct forms throughout: `scripts/odoo_probe_invoicing.py`.

Behavioural note observed: importing child contacts (file 2) **auto-promoted 24/40 parent partners to `is_company=True`** — Odoo flags a partner as a company when contacts are attached under it; the remaining 16 (no child contact) needed the explicit RPC write.

### Odoo 19 import wizard — res.partner company/individual flag is NOT importable (verified on Odoo Online 19.3, Jun 2026)

Empirically confirmed against the live wizard over three import-test runs: the `res.partner` import wizard exposes **no field for the company-vs-individual distinction** — neither `is_company` (boolean) nor `company_type` appears in the field picker. In fact **`company_type` is not even a field on `res.partner` in saas-19.3** — reading it via RPC raises `ValueError: Invalid field 'company_type' on 'res.partner'`; `is_company` (stored boolean) is the only flag field, and `RPC write({'is_company': True})` is the confirmed way to set it (the wizard cannot) (searched "company", "type", "individual"; only "Company" many2one, "Company / Database ID/External ID", "Company ID" (=company_registry), "Related Company", "Account Represented Company", and "Address Type" (=`type`: contact/invoice/delivery) exist). A CSV header named `is_company` AUTO-MAPS onto the many2one **`company_id` ("Company")** tenant field and hard-fails Test with `No matching record found for name 'True' in field 'Company'` (and on an earlier attempt produced the multi-company AccessError "...switching to the company: True"). A header `company_type` simply stays unmapped (warning), so rows import as Individuals. **Conclusion: omit any company-flag column from the wizard CSV; wizard-imported partners land as Individuals, and `is_company=True` must be set afterward via the external API (`load()`/`write`) against the same External IDs — which updates the rows in place.** This makes the wizard a partner-data loader only; the real migration should prefer the JSON-2 API. Collateral gotcha seen in a failed batch: a many2many tag created mid-transaction (`category_id` = a new tag name) rolls back with the batch, and later rows then fail with "Record does not exist... (res.partner.category(N,))" — not an independent bug; pre-create referenced tags once via Contacts ▸ Configuration ▸ Contact Tags. General rule: with "more than one error per 10 records, interrupted", fix the FIRST error and re-run — the rest is usually fallout. Note: Odoo 19's Test result is just "Everything seems valid." with no record count (count appears only at the Import confirmation).

### Odoo Online — versions, API, import (verified Jun 2026)

Current line **Odoo 19** (Sept 2025); Odoo Online runs intermediary SaaS releases (~2–3 months) — 19.3 current as of May 2026 — with mandatory rolling auto-upgrades (https://www.odoo.com/documentation/19.0/administration/upgrade.html).
- **JSON-2 API (new in 19, the one to use):** `POST /json/2/<model>/<method>`, body `{ids, context, <named params>}`; headers `Authorization: bearer <API key>`, `Content-Type: application/json`, optional `X-Odoo-Database` (Online DB name = subdomain). Per-database interactive docs at `/doc`; version discovery `GET /web/version`. XML-RPC (`/xmlrpc/2`) and JSON-RPC (`/jsonrpc`) are deprecated, removal scheduled Odoo 22 (~fall 2028). Each call is its own SQL transaction — no multi-call transactions; prefer `search_read` and batch methods. (https://www.odoo.com/documentation/19.0/developer/reference/external_api.html)
- **API keys:** Preferences ▸ Account Security ▸ New API Key; **max lifetime 3 months**, shown once. Recommended: dedicated bot user with minimal rights.
- **Online vs .sh/on-prem:** no custom modules, no shell/DB access; Studio for fields/views/automations (sandboxed-Python automation rules exist); daily backups + ZIP download via database manager. (https://www.odoo.com/documentation/19.0/administration/odoo_online.html)
- **Import:** any list view ▸ Action ▸ Import records (CSV/XLSX, per-model templates, Test-before-Import). **External ID column `id` (stored in `ir.model.data`) makes re-imports idempotent — matching ID updates instead of duplicates.** Relational columns: `Field` (name match), `Field/Database ID`, `Field/External ID` (use this cross-system); many2many comma-separated; one2many as extra rows. Dates ISO 8601, datetimes stored UTC. API-side `load(fields, data)` (callable via `/json/2/<model>/load`) takes importer-style columns incl. `/id` and returns `{ids, messages}` instead of raising; `create` is stricter. (https://www.odoo.com/documentation/19.0/applications/essentials/export_import_data.html)
- **Models:** `res.partner` (`is_company`, `parent_id`), `crm.lead` (leads AND opportunities, `type` flag), `crm.stage`, `crm.team`, `mail.activity`, `mail.message` (chatter — importing with original authors/dates is feasible via API create but not officially documented; verify on the test DB), `ir.attachment` (base64), `account.move`, `product.template`/`product.product`, `res.users` (internal vs portal). Helpdesk app (`helpdesk.ticket`/`helpdesk.team`/`helpdesk.stage`, SLA policies) included on Online paid plans — exact technical model names are Enterprise-source, confirm via the instance's `/doc` before mapping (https://www.odoo.com/documentation/19.0/applications/services/helpdesk.html).
- **Import order:** users/teams/stages/products → companies → child contacts → leads/tickets → activities/messages/attachments → invoices. Invoice history practice: import open invoices, attach historical PDFs, don't re-book closed years.

### Pipedrive — extraction (verified Jun 2026)

- **API v2** at `https://{companydomain}.pipedrive.com/api/v2/...` covers deals, persons, organizations, activities, products, deal-products, pipelines, stages, search, Fields (since Dec 2025), Projects (May 2026). **v1-only:** notes, files, mailbox, users, leads, filters, webhooks, call logs, currencies. v1 endpoints with v2 equivalents were guaranteed only to Dec 31 2025; third parties cite a July 31 2026 full v1 stop (unconfirmed by Pipedrive) — **extract v1-only entities early**. (https://pipedrive.readme.io/docs/pipedrive-api-v2, https://developers.pipedrive.com/changelog)
- **Auth:** personal API token of an **admin** user (Company settings ▸ Personal preferences ▸ API, or https://app.pipedrive.com/settings/api), passed as **`x-api-token` header**. OAuth is for Marketplace apps — unnecessary for an internal one-off.
- **Rate limits:** daily token budget = 30,000 base × plan multiplier (Lite 1×, Growth 2×, Premium 5×, Ultimate 7×) × seats; resets midnight server TZ; 429 when exhausted. v1 costs: list 20 tokens, single 2, search 40; v2 ≈ half. Burst per 2 s: 20/40/100/120 by plan. Headers `x-ratelimit-*`, `x-daily-requests-left`. Per-deal flow calls dominate a full export's budget. (https://pipedrive.readme.io/docs/core-api-concepts-rate-limiting)
- **Pagination:** v2 cursor (`cursor`+`limit`, max 500, `additional_data.next_cursor`); v1 offset (`start`+`limit`, max 500).
- **Key endpoints:** `/api/v2/deals?status=...` (deleted visible only 30 days), `/api/v2/persons` (emails/phones as `{value,label,primary}` arrays; custom fields nested under `custom_fields`), `/api/v2/organizations`, `/api/v2/activities`, `/api/v2/pipelines`, `/api/v2/stages`, `/api/v2/deals/{id}/products`; v1: `/v1/notes`, `/v1/files` + `GET /v1/files/{id}/download` (files with `remote_location`=Google Drive are links, not blobs), `/v1/users`, `/v1/leads`, `/v1/mailbox/mailThreads` → `/mailMessages/{id}?include_body=1` (only synced/Smart-BCC mail). Custom-field defs via Fields endpoints — keys are account-specific 40-char hashes; dump defs FIRST to map keys→names and enum option IDs→labels.
- **Deal stage history:** per-deal only — `GET /v1/deals/{id}/flow` (incl. stage changes) / `/changelog`. N+1 cost; budget accordingly.
- **UI export** (account menu ▸ Tools and apps ▸ Export data; XLSX/CSV, downloads live 28 days) covers deals/people/orgs/leads/products/activities/notes but **misses emails, actual file blobs, and stage history; no full-account backup exists** — the API is the completeness path. (https://support.pipedrive.com/en/article/exporting-data-from-pipedrive)

### Jira Service Management Cloud — extraction (verified Jun 2026)

- **Issue enumeration:** old `/rest/api/{2,3}/search` is REMOVED (410 since late 2025). Use `GET|POST /rest/api/3/search/jql` with `nextPageToken` pagination (no `total`, no `startAt`), explicit `fields` (default returns IDs only), `expand=changelog,renderedFields`; `jql=project=KEY ORDER BY created ASC`. - **Auth:** basic auth `email:api_token` still current; tokens now **expire (max 1 year)** and legacy ones were force-expired Mar–May 2026 — mint fresh. Rate limits: points-based quotas (Mar 2026) apply to Forge/Connect/OAuth apps; plain API-token traffic keeps burst limits (~100 RPS GET, 50 RPS PUT/DELETE; per-issue writes 20/2s). Honor 429 + `Retry-After`. (https://developer.atlassian.com/cloud/jira/platform/rate-limiting/)
- **servicedeskapi** (`/rest/servicedeskapi/`, `start`/`limit`/`isLastPage` paging): `/servicedesk`, `/servicedesk/{id}/requesttype`, `/servicedesk/{id}/customer` (**experimental — header `X-ExperimentalApi: opt-in`**, returns emails), `/organization` + `/organization/{orgId}/user`, `/request/{key}?expand=sla,requestType,participant,status`, `/request/{key}/sla` (per-metric cycles, breached flag, elapsed/remaining ms), `/request/{key}/approval`, `/request/{key}/feedback` (CSAT). Backup Manager: ZIP of XML (`entities.xml`), optional attachments, 48 h between runs, **excludes Assets** and app data — safety net, not a migration source. Portal-only customers CSV: admin.atlassian.com ▸ User management ▸ JSM ▸ Export customers. Assets (if used): UI CSV per object type, or REST via `GET /rest/servicedeskapi/assets/workspace` → `https://api.atlassian.com/jsm/assets/workspace/{wsId}/v1/...` AQL.

GDPR: user emails hidden unless profile visibility allows; JSM endpoints above return customer emails.
