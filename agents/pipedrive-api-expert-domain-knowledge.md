### 2026-08-14 — `changelog.change_source` is the automation-vs-human discriminator; and the safe way to list deals with all custom fields
`GET /api/v1/deals/{id}/changelog?limit=100` (cost 20 units, `cursor`+`limit` paging) returns per-field-change rows carrying **`change_source`** ∈ {`app`, `api`, `automation`, `web-forms`, `lead`} plus **`change_source_user_agent`** — which names the integration outright (`Zapier`, `Leadfeeder`) even though `actor_user_id` is just the token owner. This is the cheapest way to prove what a process automated vs what humans typed, and it also reveals how a record was created (`add_time` row's source = `web-forms` / `lead` / `app`). Sibling `GET /v1/deals/{id}/flow` costs 40 units and adds notes/emails inline — usually not worth it. **Listing caveat:** `GET /api/v2/deals` caps its `custom_fields` param at **15 keys**, so it cannot return an account with 18+ deal custom fields in one pass; `GET /api/v1/deals?status=all_not_deleted&limit=500` returns **every** custom field inline as hash keys, and since v1 `/deals` has no `pipeline_id` param the safe pattern is one 500-row page + **client-side `pipeline_id` filter** (416 rows → 44 for pipeline 14), cross-checked against `GET /v2/deals?pipeline_id=14&status=open|won|lost` (id sets matched exactly; 0 off-pipeline rows, so **v2's `pipeline_id` filter is genuinely applied** — unlike v1 `/files?deal_id=`). `status=deleted` on v2 surfaces soft-deleted deals that `all_not_deleted` hides. Verified rate limits (docs, 2026-08-14): daily budget = **30,000 × plan multiplier × seats** (Lite 1 / Growth 2 / Premium 5 / Ultimate 7); burst per **rolling 2-second** window per api_token = 20/40/**100**/120 by plan — Data Egret's live header `x-ratelimit-limit: 100` ⇒ **Premium**; headers are `x-ratelimit-limit|-remaining|-reset` and `x-daily-requests-left` (the last one still never appeared in our responses). ### 2026-07-27 — ★ `/v1/files?deal_id=` SILENTLY IGNORES the filter (and the general lesson about trusting query params)
Asking `/v1/files?deal_id=1041&limit=100` returned **100 files that had nothing to do with the deal** — the oldest dated 2017 — i.e. the endpoint answered with the head of the whole file collection and the `deal_id` filter was discarded with **no error and no warning**. A caller that trusts the parameter concludes "this deal has 100 attachments" when the true answer is **zero**. Correct approach: page `/v1/files` (newest-first via `sort=add_time DESC`) and **filter client-side on each row's `deal_id`**, stopping once `add_time` predates the deal's creation. This is why `scripts/pipedrive_files_filtered.py` exists in the migration repo. **Generalize it:** on the v1 surface, never assume a documented filter was applied — assert that the returned rows actually satisfy it before treating the response as an answer, and report the count you *verified*, not the count the endpoint handed back. (Same failure class seen the same day on easybill's `/documents?text=`, and easybill's `/customers?company_name=` turned out to be **exact-match**, which silently hid a customer whose real name had a suffix — cross-system lesson: a zero-hit filtered search is not proof of absence.)
