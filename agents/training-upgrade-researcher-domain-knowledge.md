## 2026-09-08 — Findings: DBA2 17→18 run (84 items) + the KB-consultation lesson

Completed `dba2-pg17-to-pg18-proposal.md`. **The single biggest process lesson: delegating every behaviour claim to `pg-kb-answerer` caught five errors in my own draft.** Do this on every future run — it is cheap and it is the difference between the DBA1 `dba-03-07` failure and a clean proposal. My five corrected claims were: (1) `io_combine_limit` is a **PG 17** GUC, not 18 (only `io_max_combine_limit`/`io_method`/`io_workers`/`io_max_concurrency` are new); (2) io worker process titles carry an **index** — `postgres: io worker 0`, not bare `io worker`; (3) `ANALYZE ONLY parent` **still samples the partitions** — it only skips storing per-partition stats (I had written "without touching the partitions", which is false); (4) the `pg_combinebackup --link` caveat I quoted is from the **release notes**, not the reference page — two different texts, cite each correctly; (5) `pg_basebackup --incremental` "plain format only" is wrong for **17 as well as 18** — it was a pre-existing error, not a version drift.

**Verified 17→18 facts (stable, reusable — cite these next time):**
- **AIO is READS-ONLY in 18.** Three greps prove it: `pgaio_io_start_writev()` has zero callers; there is no `FileStartWriteV`/`smgrstartwritev` in the tree; `FlushBuffer()` → `smgrwrite()` → `mdwritev()` → `pg_pwritev()` is byte-identical to 17. Any "better checkpoint behaviour"/"smooths writes" claim is false. The trap that generates it: `src/backend/storage/aio/README.md` discusses WAL writes and writeback pacing as *design rationale*, not shipped behaviour.
- **PG 17 vs 18 AIO history:** 17 = read stream API (`read_stream.c`, absent in 16) + `io_combine_limit`, still synchronous with `posix_fadvise`. 18 = the async engine (`io_method` default `worker`, `io_workers` 3, `io_max_concurrency` -1, `pg_aios`). "Foundation in 17" is misleading on a slide.
- `debug_io_direct` still developer-only in 18; docs say verbatim "Currently this feature reduces performance, and is intended for developer testing only."
- `effective_io_concurrency` 1→**16**, `maintenance_io_concurrency` 10→**16** (`bufmgr.h:161-162`); 17 had a `#ifdef USE_PREFETCH` 0/0 fallback that 18 deleted. 17 docs said e_i_c "only affects bitmap heap scans"; 18 dropped that restriction.
- `catversion.h` for 18 = **202506291** → tablespace dir `PG_18_202506291`.
- **EXPLAIN ANALYZE prints `rows=%.2f` unconditionally** (`explain.c:1844`), even at loops=1. Estimates keep `rows=%.0f` (`:1799`). Plus BUFFERS on by default and `Index Searches: N`. Every captured plan in every track changes.
- **`\d+` gained a `Not-null constraints:` footer** in 18 (`describe.c`, guarded by `if (verbose)`), because NOT NULL is now in `pg_constraint`. Suffixes `(local, inherited)` / `(inherited)` / `NO INHERIT` / `NOT VALID`. Hits every `\d+` capture of a table with NOT NULL columns.
- Vacuum GUC defaults new in 18: `vacuum_max_eager_freeze_failure_rate` 0.03 (also a reloption; 20 % success cap via non-configurable `MAX_EAGER_FREEZE_SUCCESS_RATE`; **no eager scanning under 8192 blocks / 64 MB**); `autovacuum_vacuum_max_threshold` 100 000 000 (caps the dead-tuple path only, **not** the insert path); `autovacuum_worker_slots` 16 `PGC_POSTMASTER` while `autovacuum_max_workers` stayed 3 but moved to `PGC_SIGHUP`; `vacuum_truncate` GUC `true`; `track_cost_delay_timing` off; `log_lock_failures` off (note the plural — renamed from the singular during the cycle, commit `73bdcfab3`).
- `delay_time` is the **only** new column in `pg_stat_progress_vacuum` and in `pg_stat_progress_analyze`; ms. `pg_stat_all_tables` gained four `total_*_time` columns (ms, include delay sleep, `total_vacuum_time` excludes VACUUM FULL).
- **VACUUM/ANALYZE `ONLY`:** PG 17 already expanded a *partitioned* parent to its partitions; what 18 added is the `ONLY` opt-out plus *legacy inheritance* coverage. `VACUUM ONLY` on a partitioned table warns `has no effect`.
- **`ANALYZE VERBOSE` was silent on resource stats in 17** (gated on autovacuum, emitted at LOG); 18 emits at INFO for manual runs with a new `finished analyzing table …` header and a new `WAL usage:` line. `VACUUM VERBOSE` renamed **"misses" → "reads"** in `buffer usage:` and gained `eagerly scanned` + `buffers full`.
- Backup: `pg_verifybackup` dates from **v13** (not 17) and gained tar-format verification + `-F p|t` in 18, with format auto-detected by `stat()`ing `PG_VERSION`; WAL parsing is still plain-only (`-n` required for tar, and it is a hard error). `pg_combinebackup` gained only `-k/--link` in 18. `wal_summary_keep_time` (default 10 days, `GUC_UNIT_MIN`) — the name `wal_summarize_keep_time` **does not exist in any version**. `pg_ls_summariesdir()` new in 18.
- `idle_replication_slot_timeout` default **0 = disabled**, seconds. Applies to physical slots including `pg_receivewal`'s — but only once the slot has actually streamed (`--create-slot` passes `reserve_wal = false`, so a fresh slot has invalid `restart_lsn` and is not yet eligible). Invalidation is **not** recoverable; invalidation happens at checkpoint.
- **Recovery log wording is almost entirely unchanged 17→18** — all `starting point-in-time recovery to …`, `recovery stopping …`, `restored log file …`, `selected new timeline ID` are byte-identical; LSNs still `%X/%X`. Four exceptions: `checkpoint complete:` gained `, wrote %d SLRU buffers` (and `;`→`,`); failed startup lost `aborting startup due to startup process failure` and now logs a four-line shutdown sequence; `archive_timeout` is quoted in the WAL-switch message; `pg_tblspc/` lost its trailing slash. Useful for judging PITR demo re-captures.
- **checksums + `pg_upgrade` trap:** `initdb` default flipped to on in 18, and `pg_upgrade` has three fatals in `controldata.c:check_control_data()` with **no override**. Remedies: `initdb --no-data-checksums` on the new cluster, or `pg_checksums --enable` on the stopped old one. Restore direction is safe — checksum state lives in `pg_control`, so a restored 17 base backup stays non-checksummed. Also `pg_basebackup` can now *fail* backups it used to pass, because verification finally has something to verify.
- **libpq 18 defaults `max_protocol_version` to 3.0, not `latest`** (`fe-connect.c:pqConnectOptions2()`, with the comment "To not break connecting to older servers/poolers that do not yet support NegotiateProtocolVersion"). `PG_PROTOCOL_LATEST` is 3.2. So 256-bit cancel keys are opt-in, PgBouncer (3.0-only) is unaffected, and "PG 18 clients use 3.2" is a wrong claim.
- **PgBouncer CVE-2025-12819** (fixed 1.25.1): unauthenticated SQL execution via a hostile `search_path` in the StartupMessage, when `track_extra_parameters` includes `search_path` + `auth_user` set + unqualified `auth_query`. Upstream explicitly ties condition 1 to **PostgreSQL 18**, because 18 made `search_path` GUC_REPORT. Good direction-two material for any pooling chapter.
- **Currency as of 2026-09-08** (refresh every run): 18.6 / 17.11 / 16.15 / 15.19 / 14.24, all released **2026-08-13** with 19 Beta 3. **18.5 was never released** (regression found post-wrap) — say so, it looks like an error otherwise. EOL: 14 → 2026-11-12 · 15 → 2027-11-11 · 16 → 2028-11-09 · 17 → 2029-11-08 · 18 → 2030-11-14. Next minor 2026-11-12. Tools: pgBackRest **2.59.1** (2026-08-17), WAL-G **v3.0.9** (2026-08-20), Barman **3.20.0** (2026-08-27, now needs Python 3.12), PgBouncer **1.25.2** (2026-05-08).
