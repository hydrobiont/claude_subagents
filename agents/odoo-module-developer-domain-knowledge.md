### 2026-09-29 — `IrModelData._process_end`, confirmed from source, deletes a record your own code created if you leave its xmlid `noupdate=False` and nothing else references it

`odoo/addons/base/models/ir_model.py::_process_end(modules)` runs once, at the end of loading
EVERY module being installed or updated in that run (after all of that module's own data files,
including a `<function>` tag that runs your Python, have already loaded and committed their
writes). Its query: `SELECT ... FROM ir_model_data WHERE module IN %s AND res_id IS NOT NULL AND
COALESCE(noupdate, false) != true` — every external id of the processed module(s) that is NOT
noupdate, in one pass. For each such row, if its xmlid string is not in `self.pool.loaded_xmlids`
(populated by the declarative `<record>`/`<template>` XML loader — a raw `env["ir.model.data"]
.create(...)` call from inside arbitrary Python, e.g. a get-or-create helper, never adds to it),
the record is either (a) reduced to "just remove this one xmlid row" if the SAME (model, res_id)
carries ANOTHER external id, or (b) `record.unlink()`'d outright if this was its ONLY external id
— and Odoo's many2many relation tables use `ON DELETE CASCADE`, so deleting the record silently
empties every m2m field that pointed at it, on every model, with no error anywhere. A get-or-
create helper that registers its own xmlid with the default `noupdate=False` is therefore SAFE
only for a row that will always have another, protected external id (e.g. one also carried by a
migration/demo data file) — a genuinely NEW record (nothing else names it) is deleted the very
first time the module updates, taking every relationship into it down at the same time. Fix:
register such an xmlid with `noupdate: True` on create, AND upgrade an existing unprotected row
found already that way (`if not xmlid.noupdate: xmlid.write({"noupdate": True})`) — a database
that updated through an unprotected version needs the repair applied to it, not just to future
installs. A CI database can mask this completely: on a fresh install with no other xmlids ever
competing for the same records, `_process_end` deletes ALL such rows uniformly and a test that
calls the same get-or-create helper at the top of its own body just silently re-creates them
under new ids, so the tally stays green while a real database (carrying other, protected xmlids
for only SOME of the same records — e.g. three of four reused tags with a migration-era xmlid,
one brand-new tag with only this module's) breaks asymmetrically. Root-caused in `de_sla`
(`HelpdeskTicket._de_sla_class_tags`, `de_sla/models/helpdesk_ticket.py`) after the 2026-09-29
staging install (build 37822891) left four generated SLA policies with empty `tag_ids` and their
tickets with no class tag; precedent for the fix: `dataegret_slackbot` 19.0.3.2.1 (commit
`2ae1b5f`, "protect runtime ticket XMLIDs") already did the create-time half (`"noupdate": True`
on its own `ir.model.data.create()` call) for a different, runtime-created xmlid.

### 2026-09-29 — `BaseModel.unlink()` is a faithful stand-in for `_process_end`'s own record deletion, and a generator's exact-key adoption self-heals a tag-less managed record for free

Confirmed from `odoo/orm/models.py::unlink()`: deleting a record explicitly (`record.unlink()`)
issues a raw SQL `DELETE` (which is what triggers PostgreSQL's `ON DELETE CASCADE` on any
many2many junction table pointing at it) and then explicitly searches and unlinks any
`ir.model.data` row with that `(model, res_id)` — the exact same two effects `_process_end`
produces on a record it decides to delete. A test that wants to reproduce "this module's own
earlier update let `_process_end` delete one of our records" therefore does not need to simulate
`loaded_xmlids`/`_process_end` at all: create the fixtures, then call `.unlink()` directly on the
target record, and the many2many/xmlid damage is identical. Separately, in a generator that
adopts an existing target record by an exact marker-field match before falling back to a fuzzy
match (this codebase's `de.sla.generator._de_find_for_adoption`: exact `de_profile_key` first,
then a fuzzy equal-tag-set/overlapping-partners search that is active-only and cannot match an
emptied tag set), a record whose relationship was wiped this way is adopted straight back onto a
freshly re-resolved related record — with a corrective diff-write, same id, no duplicate — PURELY
because the marker field survived the wipe and the next full regeneration run recomputes the same
key for the same input. This means the generator's own periodic re-run is already most of the
self-repair; the only genuinely new work needed for a `de_sla`-shaped incident was relinking the
now-orphaned side (the ticket's `tag_ids`, which the tag deletion also cascaded off of and which
no generator pass ever revisits on its own — the generator only walks `helpdesk.sla`, never
`helpdesk.ticket`), done under `_backfill()`'s own trusted, `_sla_reset_trigger`-bypassing context
so relinking a class tag does not reset or recompute the ticket's SLA status history.

### 2026-09-28 — In the `de_course_booking` repo, `staging_migration` is kept in sync with `dev/booking-intake` by repeated MERGE commits, not fast-forward — check `git merge-base --is-ancestor` before assuming a plain push will work

`git log origin/staging_migration` shows three "Merge dev/booking-intake into staging_migration" commits (`48fc6a4`, `64afd7f`, `97de7b0`), and `git merge-base 50f3763 origin/staging_migration` resolves to `bb42908`, an EARLIER commit than `50f3763` (`dev/booking-intake`'s own base, which is also `prod`'s current tip) — meaning `staging_migration`'s history has genuinely diverged from both `dev/booking-intake` and `prod`, not merely fallen behind on a shared line. ### 2026-09-28 — `ir.ui.menu.groups_id` is `group_ids` in Odoo 19; `crm.lead.description` is `fields.Html`; an `ir.actions.act_window` Char field's `eval="…ref(...)…"` is a safe, confirmed pattern

Three source-verified facts from building the `de_course_booking` Course-pipeline menu. (1) `odoo/addons/base/models/ir_ui_menu.py` on the `19.0` branch: the menu-visibility field is `group_ids = fields.Many2many('res.groups', 'ir_ui_menu_group_rel', 'menu_id', 'gid', ...)` — the historic `groups_id` name (still what the `groups="..."` XML attribute on `<menuitem>` writes to) is gone, same rename pattern as `res.users.groups_id`→`group_ids` and `crm.stage.team_id`→`team_ids` already on file below (2026-08-17). (2) `odoo/addons/crm/models/crm_lead.py`: `description = fields.Html('Notes')` — an HTML field, not Text; any payload-derived string placed into it must be escaped by hand (stdlib `html.escape` is sufficient) before building the markup, since a raw `<`/`&` from user input would otherwise be parsed as markup by Odoo's `html_sanitize` rather than displayed as text. (3) `odoo/orm/fields_textual.py`: `Char`/`BaseString.convert_to_cache` does `s = str(value)` for anything that isn't already `bytes`/`str` — so `<field name="domain" eval="[('team_id', '=', ref('xmlid'))]"/>` on an `ir.actions.act_window` (a plain `Char` field) is a fully safe, ORM-confirmed pattern: the XML loader's `eval` evaluates the Python list with `ref()` resolved to a real id, and the Char field's own conversion stringifies it into exactly the domain-string form `safe_eval` expects later. This is the same mechanism already relied on for `context` fields (`action_booking_mail_templates` in this module) — now confirmed by source rather than by analogy alone.

### 2026-09-28 — `request.update_env` fixes two distinct identity leaks with the same one call, not just the ORM's own default_env check

Confirmed from `odoo/http.py` on the 19.0 branch: `update_env(self, user=None, context=None, su=None)` rebinds `self.env` **and** `self.env.transaction.default_env`, and accepts `user` as either an int or a `res.users` recordset. The 2026-08-17 entry below documents one failure mode this fixes — the ORM's own relational-field access checks, which run against `transaction.default_env.uid` rather than whatever env a controller derives later. A second, distinct failure mode is application code that reads `request.env.uid` directly as "who is making this request" (for example `de_portal`'s `_de_portal_acting_user()`, gating a `helpdesk.ticket.create` on the acting user's `.share`) — a route that only ever does `env = request.env(user=SUPERUSER_ID, su=True)` for its own work never touches `request.env` itself, so `request.env.uid` stays whatever the public route was authenticated as, and any guard reading it sees the wrong principal even though every write in the request runs correctly as the intended user. `request.update_env(user=...)`, called once (for instance right after a signed request's HMAC check passes, as `dataegret_slackbot` 19.0.3.2.3 now does in `_verify_signature()`), fixes both at once because it is `request.env` itself that changes, not a value derived from it.

### 2026-09-28 — Odoo 19's ORM package split moved field-type internals: `Selection._description_selection` now lives in `odoo/orm/fields_selection.py`

Confirmed by listing `odoo/orm/` on the 19.0 branch (github.com/odoo/odoo): the old monolithic `odoo/fields.py` no longer holds every field type — it now covers only the base `Field` class, with each type split into its own module (`fields_binary.py`, `fields_misc.py`, `fields_numeric.py`, `fields_properties.py`, `fields_reference.py`, `fields_relational.py`, `fields_selection.py`, `fields_temporal.py`, `fields_textual.py`), and the flat `odoo/fields.py` path from pre-19 Odoo 404s directly on the 19.0 branch. `Selection._description_selection(self, env)` (in `fields_selection.py`) is unchanged in shape from pre-19 Odoo: it returns a list of `(value, label)` pairs, translating labels via `ir.model.fields.get_field_selection` for a static selection, or resolving through `determine(selection, env[model_name])` for a callable/string selection — the API a helper can use to read a Selection field's live allowed values (`{value for value, _label in field._description_selection(env)}`) without hardcoding the vocabulary. Read this file, not the old top-level path, whenever a Selection field's own description/values/export behaviour needs confirming from source on Odoo 19.

### 2026-09-28 — Stripe Checkout's billing/name/email/card prefill comes only from a saved card, never from bare `Customer.address`/`.name`

Read from Stripe's own docs (docs.stripe.com/payments/existing-customers, "Prefill fields on the payment page") and confirmed live against `de_course_booking` on production: Checkout prefills Email, Name, Card and Billing address on the payment page only when the passed `customer` has a **saved card** (a previously-used, `allow_redisplay: always`-eligible payment method) whose stored `billing_details` satisfy the session's `billing_address_collection` — `required` demands email + name + every address field on that saved card. Creating a `Customer` with `name`/`address[...]` and passing `customer=cus_...` to a fresh Checkout Session does **not** by itself prefill anything beyond what a saved card would carry — a brand-new customer (first-ever payment) has no saved card, so the billing form renders empty regardless of how complete the Customer object is, and `customer_update[address]=auto`/`[name]=auto` only controls whether Checkout *writes* what the buyer types back onto the Customer afterward, not whether it reads from it beforehand. A module that wants repeat-customer prefill on a later booking additionally needs the first successful payment's PaymentIntent to actually save a reusable card (e.g. `payment_intent_data[setup_future_usage]`) — without that, even a returning customer's Checkout stays unprefilled forever. Do not treat "the module creates/reuses a Stripe Customer carrying the address" as sufficient for prefill; it is necessary only for Stripe Tax and for the eventual invoice, not for the payment page.

### 2026-09-28 — Stock CRM's default "Pipeline" window action carries no `team_id` domain; multiple teams' opportunities show together unless a team-scoped action or explicit domain is used

### 2026-09-26 — A wizard button that returns `True` or `None` closes its dialog; only a browser click reveals it

`de_sla`'s change wizard passed its whole unit suite on dev build 38671012 while its **Preview impact** button was unusable: `action_preview` ended with `return True`, and the web client closes a `target="new"` dialog whenever a button method returns no action. `call_button` reports that non-action return as `{"result": false}`; nothing is logged, no toast or console error appears on either side, and the previewed transient record is simply abandoned, so **Apply** could never be reached. `Form` tests and direct `wizard.action_x()` calls never model the dialog, so CI and the badge stay green. The fix is the standard idiom: return an `ir.actions.act_window` that reopens the same record (`res_model`, `res_id`, `view_mode: form`, `target: new`) and passes `dict(self.env.context)` through, so a view rule keyed on a `default_*` context key (here the pinned classification) still holds after the reopen; a button that is meant to finish the wizard returns `ir.actions.act_window_close`. Rule: every wizard button method returns an action, and browser QA of a wizard clicks every button and checks the dialog is still open in the expected state, reading the raw `call_button` response when it is not.

### 2026-09-24 — Five first-hand facts from the de_fin_mail 19.0.1.3.x work (verified in this session, added by the coordinating session)
- `message_post(attachment_ids=[...])` links a record's OWN existing attachments to the message (`_process_attachments_for_post` keeps every id for an internal user; only composer-owned attachments get re-parented), so the invoice PDF can be attached to an outgoing message without duplicating its bytes.
- `account.move._message_post_after_hook` treats a posted message with attachments and `message_type` in {email, comment} as a bill to import; pass `disable_attachment_import=True` in the context when posting notes with attachments on invoices, and post outgoing uploads as `email_outgoing` (never processed).
- In tests, `mock_mail_gateway()` defaults to `mail_unlink_sent=False`, which keeps every sent `mail.mail` row alive; use `mock_mail_gateway(mail_unlink_sent=True)` when the code under test relies on `auto_delete` (otherwise a surviving row looks like a failed send).
- Over XML-RPC on Odoo 19, `create` called with a list of value dicts returns a LIST of ids even for one record; pass `[id]` or index `[0]` before using it as a many2one value (`partner_id: [139]` raised a PostgreSQL "integer[]" datatype error).
- A dev build has no `admin/admin`; open it through the dashboard card's Connect link (single sign-on), then set a throwaway admin password with `res.users.write({'password': ...})` over the page's `/web/dataset/call_kw` and use XML-RPC; the change invalidates the browser session, log in again with the new password if the UI is needed.


### 2026-09-24 — Automating Gmail's own settings UI has UI behaviours distinct from Odoo's own UI

Setting up a Gmail-side forwarding address and filter (to route a vendor's automated reply mail into an Odoo alias) in the persistent browser profile requires handling several things Odoo's own UI does not have. Adding a forwarding address triggers Google's own identity check, and the verification email carries no numeric code — only a confirmation link that must be opened and confirmed. Saving a filter that forwards mail asks for two separate confirmations in sequence (a filter-creation dialog, then a Google sign-in popup); navigating away before the second one resolves discards the filter with no error and an empty filter list afterward. The filter action panel's checkbox inputs render one pixel wide and off-screen, so automation must click the adjacent label text rather than the input itself, and the address chooser is a custom listbox rather than a native select element; a DOM-level `.click()` call ticks a checkbox but does not persist the final "Create filter" action, which needs a real click event. Keep account-wide forwarding set to "Disable forwarding" and let the individual filter perform the forwarding.

### 2026-09-24 — The DATEV upload-confirmation loop runs fully automatically, confirmed within about two seconds of a reply arriving

`de_fin_mail` mails each customer invoice's PDF, on send, to the address in system parameter `de_fin_mail.datev_upload_email`. The standing proof that DATEV actually accepted a document is DATEV's own automatic reply, not the "sent" note recorded on the invoice — that note only proves Gmail accepted the outbound message, not that DATEV did. DATEV's confirmation sender replies from `noreply@uploadmail.datev.de` within seconds of every upload, quoting the upload mail's Message-ID in `In-Reply-To`/`References`, and its body lists which files it accepted by name with a count. As of 2026-09-24 that reply reaches Odoo automatically: a Gmail filter on the shared `connect@` mailbox forwards mail from that sender into an Odoo mail alias, and the module's gateway hook matches the reply back to the originating invoice and marks it confirmed — verified live end to end (cron feed, DATEV reply, Gmail forward, Odoo alias, invoice confirmed) within about two seconds. A manual forward of a DATEV confirmation into the same alias reaches the same verdict, matched by the invoice number quoted in the subject rather than by the Message-ID. DATEV silently ignores any file extension it does not recognise (a companion e-invoice XML sent alongside the PDF is never listed, accepted or rejected), and returns a distinct SMTP rejection to a sender it has not authorised rather than a normal reply.

### 2026-09-24 — The mail gateway parses the HTML alternative of an inbound reply, not the plain-text part

A parser written against a plain-text email body can still fail on a real reply, because Odoo's mail gateway keeps the HTML alternative of a multipart message rather than the plain-text one. `de_fin_mail`'s first parser for DATEV's confirmation required a literal "- " before each filename, matching the plain-text layout; the live HTML alternative renders each filename inside a bare `<li>` with no leading dash, and the message's `<style>` block and CSS rules survived Odoo's HTML sanitising into the text the parser read, corrupting the stored excerpt. The fix: match filenames by file extension anywhere in the text instead of after a fixed prefix, and strip `<style>` blocks, CSS comments and brace-delimited rule bodies before parsing. General lesson: test inbound-mail parsing against the actual HTML body a real sender's mail client produces, not a hand-written plain-text fixture — a passing unit test built from the wrong body shape is not evidence the parser works on real mail.

### 2026-09-24 — Production module updates: a fast-forward push, a short window of 503s, then the new version reads back live

Deploying to production is a fast-forward push of the addons repository (`git push origin <sha>:prod`); odoo.sh then restarts the production build to pick up the manifest version change. Observed during the `de_fin_mail` 19.0.1.3.0 → 19.0.1.3.1 update: the production URL answered HTTP 503 for about 30 seconds during the restart, and the new `installed_version` was confirmed shortly afterward by a read-only XML-RPC check. Plan a production deploy around a short availability gap, and confirm the update by reading the module version back rather than treating a successful git push as proof the update landed. A staging rehearsal can be skipped on the user's explicit per-change instruction ("if everything is green, deploy it") — that authorisation covers the change it was given for, not a standing exemption from rehearsal on later changes.

### 2026-09-23 — `message_route` treats an inbound mail as a forward, not a reply, when another model's alias appears in To or Delivered-To

Read from the Odoo 19 community source: an inbound mail whose References header matches a stored `mail.message.message_id` is normally routed as a threaded reply onto the record that message belongs to. That default is overridden when the To/Delivered-To/Cc set also names a mail alias belonging to a *different* model — in that case the mail routes as a new message to the alias's own model instead, even though it still carries References to an existing message; alias routing itself keys off `Delivered-To` together with To and Cc. Practical consequence for `de_fin_mail`: a DATEV confirmation reply that Gmail delivers with a `Delivered-To` header naming the `datev` alias lands on a new `de.datev.notice` record, matched back to the invoice separately through the References header, while the identical reply without that header threads directly onto the invoice. A feature whose mailbox can receive mail addressed either way needs to handle both routes.

### 2026-09-23 — `message_update` runs before `message_post`; `is_internal` in the routed dictionary picks the note's subtype; inbound author lookup never creates a partner

Odoo 19's `_message_route_process` calls a record's `message_update` before the message is actually posted, and reads `is_internal` from the routed message dictionary to decide whether the resulting note uses the internal-note subtype; the parent message's author is pinged only when a parent message actually exists. Overriding `message_update` is therefore the hook point for classifying an inbound reply before the standard chatter entry is created from it. Separately, the inbound-author lookup that matches a sender address to a `res.partner` is a `no_create` search: an unmatched sender is never turned into a new partner record as a side effect of receiving mail. `_message_post_after_hook` ignores messages of type `email_outgoing` and messages carrying no attachments, so post-processing tied to that hook will not fire for either.

### 2026-09-23 — A transport `mail.mail` linked by `mail_message_id` becomes a notification row; `auto_delete` removes only the transport, not the chatter message

To both record a message on a record's chatter and actually send it as email, post or create the `mail.message` first, then create a `mail.mail` transport row with `mail_message_id` set to that message's id. Linking it this way makes the transport `is_notification=True`, so when `auto_delete` cleans up sent mail it removes only the transport row — the chatter message, and any attachment posted with it, stay on the record. `de_fin_mail` uses this pattern for the DATEV upload: the invoice keeps a permanent chatter entry with the sent PDF attached, while the outgoing-mail row that carried it to DATEV is cleaned up like any other sent transport.

### 2026-09-23 — `AccountTestInvoicingCommon` plus `MailCommon` as the fixture base for a feature that both posts accounting entries and threads mail

A test that needs both a working chart of accounts and journals, and a real mail gateway (to exercise `mail.thread.message_process` against an actual inbound reply rather than calling an internal method directly), should inherit both `AccountTestInvoicingCommon` and `MailCommon` — a bare test database has neither journals nor a wired gateway on its own. Odoo's test-mode report rendering splits generated HTML per record before producing a PDF, which is what lets a report-generation pipeline actually run inside a test instead of being silently skipped or stubbed; `de_fin_mail`'s DATEV-upload tests rely on this to produce a real PDF attachment inside the test transaction. This combination is the mail-aware counterpart to the plain `AccountTestInvoicingCommon` requirement recorded in the 2026-07-27 entry below.

### 2026-09-23 — odoo.sh fails a module on any ERROR-level log line during its tests, independent of the pass/fail tally

Build 38535645 (`de_fin_mail`) reported `0 failed, 0 error(s) of 190 tests` in `install.log`, with `de_fin_mail: 34 tests`, yet the build's status card still read "At least one test failed when loading the modules." ### 2026-09-21 — odoo.sh's SSH gateway can refuse the registered key entirely; the dashboard's Shell tab is the fallback

The documented recipe for reading a build's `install.log` over SSH (`ssh -i ~/.ssh/odoosh_dataegret_rsa <build-id>@<build-domain>`) needs `-o IdentityAgent=none -o IdentitiesOnly=yes` on a Mac where the ssh-agent offers a YubiKey PIV key first — otherwise the connection fails on `agent refused operation` before the registered RSA key gets a turn, even though that key needs no passphrase and the exchange is otherwise non-interactive. ### 2026-09-21 — The build id needed for SSH is available only from the odoo.sh dashboard, and its browser profile can be locked by another session

odoo.sh sets no GitHub commit statuses or check runs on the addons repository, and there is no branch-level build hostname to construct from the branch name alone (`<project>-<branch>.dev.odoo.com` resolves only for a currently-live build, dead builds included, and answers nothing otherwise). The build id — the SSH username needed to read `install.log` — must be read from the odoo.sh dashboard in the persistent browser profile. That profile can be locked by another session (a `SingletonLock` file names the holding process), and a browser-automation agent correctly refuses to kill a foreign process or fall back to an isolated profile — so a CI round that needs the dashboard should check the lock first and ask the user to release it if another session holds it, rather than retrying blindly.

### 2026-09-11 — Odoo unions compute-method dependencies across the MRO; overriding a compute method without `@api.depends` does not lose the parent's dependencies

Read from the Odoo 19 framework source (`odoo/orm/fields.py`, `Field.get_depends`): the dependency list for a computed field is built by walking every implementation of the compute method along the class's MRO and collecting each one's own `@api.depends` declarations, then concatenating them. An override with no `@api.depends` of its own still runs with the base class's dependencies intact; adding `@api.depends(...)` to an override is additive, joining the inherited set rather than replacing it — decorate an override freely when it reads a field the parent implementation never declared. The `depends=` parameter passed to the field definition itself is the one exception: it replaces the MRO walk outright rather than joining it. Verify a suspected "override lost its dependencies" defect against this source before treating it as confirmed; the more common real defect is a new field the override reads that was never declared as a dependency anywhere.

### 2026-09-09 — odoo.sh installs modules and runs the entire test suite before loading demo data

An odoo.sh build runs, in order, module installation with the full test suite enabled, and only afterward a separate force-demo pass that actually loads demo records; on a build observed in full, the force-demo pass ran after the tests had already finished and failed. Any code that checks whether it is running against a demo database (for example, to decide whether to seed placeholder records) reads that check as false throughout both install and the test run, even though the finished database reports demo modules as loaded afterward. Consequence: never gate install-time seeding on a demo-database flag, and never let a test fixture depend on rows an install hook created for that reason — build fixtures explicitly in the test's own setup instead.

### 2026-09-09 — An odoo.sh dashboard URL for a slash-named branch can silently render production

A dashboard URL built from a branch name that contains a slash does not reliably address that branch: the plain path falls through to production's own history, and even a URL-encoded slash that worked on one date failed on a later one (the application rewrote the address back to its unencoded form and served production again). The only reliable confirmation of which branch a dashboard page is showing is the page's own heading, which prints the branch name; the reliable way to navigate there is the branch list in the sidebar, not a constructed URL. This matters because the same page carries the Rebuild and Merge controls, both of which act on whatever branch the page is actually showing.

### 2026-08-21 — Pushing to an odoo.sh Staging branch updates its build in place; only Rebuild re-forks production

A `git push` to a Staging-stage branch updates that branch's existing database in place, running a module update only on whichever modules changed their manifest version — it does not re-fork production. Only the branch page's explicit Rebuild control restores a fresh copy of production data. Two consequences follow: a new custom module is never auto-installed by either a push or a Rebuild, so a staging Rebuild reverts a module that a previous session installed by hand but that has not yet reached production; and because a push updates in place, iterating on a module after its first install is cheap (bump the version, push, the existing data survives) — reserve Rebuild for when a genuinely clean copy of production is actually needed. Dev branches behave differently again: every push builds from scratch with demo data and installs every module in the repository, which makes them a fast CI signal but not a rehearsal against real data, and their containers are recycled unpredictably (on the order of hours, never guaranteed) once later pushes accumulate — never treat an armed dev build as a standing test target across a later push.

### 2026-08-03 — Posted journal entries are permanently undeletable on production; cancel is the terminal state

### 2026-07-27 — The dev → CI → prod deployment loop

Branch off `prod` for a new feature; build the module following the existing addons as precedent (read-only behaviour by default, own parameters namespaced `<module>.<key>`, cron-driven work carrying a cursor that holds on failure, `ir.model.access.csv` plus own-records `ir.rule`, tests under `tests/`); bump the manifest `version` (odoo.sh updates a module on a build only when the version changes — a code-only push otherwise ships without ever loading); wrap any operational lever (a cron's active flag, a parameter meant to be tuned live) in `noupdate="1"` so it is not silently reset on the next update; push the dev branch and read the real test tally from the build container rather than trusting the status badge; optionally rehearse on staging by triggering a cron directly (its private `_cron_*` method is not RPC-callable, so use `ir.cron.method_direct_trigger`) with every outward-facing parameter pointed at a test target first; merge fast-forward to `prod`; verify the live result over read-only XML-RPC (module version, the actual view `arch_db` and not just the model, cron state, parameters, guards); then hand the finished feature to `odoo-acceptance-tester` with a spec file. Rendering a feature against realistic data catches defects mechanical correctness does not: two real user-facing defects in a digest feature survived 36 green tests and a clean staging rehearsal, and were only caught by rendering the feature's own output against production-scale data.

### 2026-07-27 — Reading a build's real test result: the status badge is not reliable evidence

For these modules, a healthy build shows "Test: Warning" with sub-status "done" — several install-time warnings are expected — while "Success" is not the signature of a healthy build here, and a badge reading "Failed" can co-list a module that has no actual failing test anywhere in the log. The authoritative record is the build container's `install.log`, read over SSH: grep the whole file (not `tail`, which drops earlier phases) for the test-count and failure-count lines and any `FAIL:` markers, adding roughly 20 lines of trailing context after a `FAIL:` match to capture its traceback. Practical notes: use `grep -a` (the log trips binary-content detection); `sftp`/`scp` are disabled on build containers, so push a file with `ssh '<command> > file' < local-file`; a shell or single-test run on the container needs an explicit `--addons-path` covering the core, enterprise and custom-addons directories; and a docutils indentation-error line from RST inside a manifest description is pre-existing noise present on green builds too, not a finding. The module-loading failure count reported during install and the overall test-result count reported at the end of the run measure different scopes (install-time tests versus the whole run, including any `post_install`-tagged tests) and can legitimately differ — state which one a reported number refers to.

### 2026-07-27 — `noupdate` determines whether an operational lever shipped in a data file survives a module update

A record loaded from a module's own data file is reset to that file's value on every module update unless it, or its enclosing data block, carries `noupdate="1"`. The sharpest case: a cron that ships disabled by design and is then enabled by hand in production gets switched back off by the very next update, with no error anywhere — a silent regression of a live feature. Wrap any record an operator is expected to tune after go-live (a cron's active flag, a live parameter) in `noupdate="1"`, with a comment naming it as the operational lever, and confirm empirically after a real update that the flag survived rather than assuming the XML attribute alone is enough. Ordinary database rows — `ir.config_parameter` values, user-created records, a module's own marker or cache fields — are not subject to this at all and survive updates regardless; what does get re-applied on every update is view architecture, menus, ACL rows and `ir.rule` domains, along with any data record not marked `noupdate`.

### 2026-07-27 — False-green trap: a suppression flag set with `with_context` on a fixture's `create()` propagates into every later call on the same recordset

A test fixture created with a suppression context flag (for example, one that disables a confirmation side effect) carries that flag forward into every subsequent `write()` or `unlink()` performed on the recordset the `create()` returned, not only the single call it was intended to scope. This silently disables the behaviour a later part of the same test is trying to exercise, and the test still passes because it asserts against a baseline of zero rather than the effect it meant to trigger — the most dangerous of the false-green traps because nothing about the test's own output looks wrong. Scope such context flags to the exact call they are needed for, and drop them from whatever recordset the test hands back for further use.

### 2026-07-27 — False-green trap: field-tracking rows materialize in a precommit hook a rollback-only test never reaches

`mail.tracking.value` rows (the rows behind a field's change history in the chatter) are created in a precommit hook, which a standard test transaction — rolled back at the end of the test, never committed — does not trigger; calling `flush_all()` alone leaves zero tracking rows even though the field write itself succeeded. Worse, a record created and then written to within the same precommit window gets no field tracking recorded at all. A test that asserts on tracking history must explicitly flush and then run `env.cr.precommit.run()` after the write. Production is unaffected by any of this, because every real HTTP request commits.

### 2026-07-27 — False-green trap: Odoo sends real mail while a test's own fixtures are still being built

Ordinary Odoo behaviour — for example, assigning an activity to a user — sends a real notification email as a side effect, independent of the feature under test. A no-mail guard that snapshots `mail.mail`/`mail.notification` counts *before* a test's fixtures run will therefore fail for a reason unrelated to the code being tested. Baseline such guards after fixture setup completes, not before it starts.

### 2026-07-27 — False-green trap: accounting tests need `AccountTestInvoicingCommon`, and some assertions must be tagged `post_install`

A bare test database has no chart of accounts and no journals, so any test that posts or reads accounting entries needs to inherit `AccountTestInvoicingCommon` rather than the plain transaction test case; some accounting-dependent assertions additionally need the `post_install` tag to run only once the full module set (and its demo/config data) has finished loading. See the 2026-09-23 entry above for the same base class combined with `MailCommon` when a test also needs to exercise the real mail gateway.

### 2026-07-27 — False-green trap: `active_test` hides archived rows from an existence or a count check

On any model with an `active` field, a plain `search`/`search_count` domain silently excludes archived records — a count of "how many reminders exist" once read 2 when 3 existed, one of them paused. Any assertion about how many records exist, or whether a specific record survived an operation, must explicitly include archived rows (`("active", "in", [True, False])`, or `context={"active_test": False}`); a paused record hidden this way is otherwise indistinguishable from a deleted one.

### 2026-07-27 — Repo hygiene: never stage everything, and commits carry no attribution trailer

Never `git add -A` in the addons repository: a local compile check once left `__pycache__` and compiled `.pyc` files staged, and they reached production before being caught. A `.gitignore` now covers `__pycache__/` and `*.py[cod]`, but adding files explicitly rather than wholesale remains the safer habit. The Slack and notification message templates in these modules are written as single Python f-strings rather than through a separate templating layer, so a wording tweak is a one-line code change — but it still rides the full dev → CI → prod flow like any other code change, including the manifest version bump, because it is still code.

### 2026-07-27 — A JS asset bundle regenerates only when the manifest version changes, and backend/frontend bundles are kept deliberately separate

### 2026-07-27 — Extend the web client through registries, not template patches; anything that feeds the chatter has a whole-database blast radius

A chatter action added through mail's own public registry function (`registerMessageAction`, `mail/static/src/core/common/message_actions.js`) survives an Odoo front-end restyle, because a `t-inherit` override of a core Owl template is coupled to the exact markup of the version it was written against and breaks silently — with no test to catch it — the next time that markup changes. Separately, any server-side override that feeds data into the chatter (for example, `mail.message._to_store_defaults`, which runs on every chatter load for every model and every user) affects the whole database if it raises or runs slowly: keep such overrides to cheap string work and field reads, never queries or external calls, because a defect there breaks chatter loading everywhere in Odoo, not only on the record type it was written for.

### 2026-07-27 — Rails that apply to any new functionality

Production is the system of record for business data; no data correction happens there without the user's explicit per-change approval, and the standing role outside an approved change is verification on request, not correction. Functional and code changes ride the dev → staging → prod deployment flow; data content never does, and source systems (JSM, Tempo, Pipedrive, easybill) are export-only. Chatter written by automation uses `mail.message.create()`, never `message_post()`, sets no `partner_ids`, and every writing script snapshots `mail.mail` and `mail.notification` counts before and after, aborting on drift; a tracked-model write additionally threads a no-track context, because customers are followers on their own support tickets and tasks and a plain field write would otherwise notify them. Every write is idempotent through an `ir.model.data` external id. Writes are single-writer: the check-then-create idempotency pattern is not atomic, and two concurrent writers once produced three orphan duplicate records from what was meant to be a single logical write.

### 2026-07-08 — Keychain service names are locations, not values; API keys expire on a roughly three-month cycle

Credentials for this programme live only in the macOS keychain (or, for anything not Odoo-specific, 1Password) — this repository, and this file, record which keychain *service* holds a given credential, never the credential's value.
