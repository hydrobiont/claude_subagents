### Parallel index builds — which AM since which PG major (verified 2026-09)
Recurring version-attribution trap on "PostgreSQL 18 builds B-tree, GIN and BRIN indexes in parallel": only **GIN** is new in 18 ("Allow GIN indexes to be created in parallel", release-18.html). **BRIN** parallel builds landed in **17** ("Allow BRIN indexes to be created using parallel workers", release/17.0), **B-tree** in 11. Authoritative check is `amcanbuildparallel` in the AM handlers: true only in `nbtree.c:137`, `ginutil.c:60`, `brin.c:272`; false for hash, gist, spgist. `maintenance_work_mem` rule (sql-createindex.html, unchanged in 18): each parallel worker needs a 32 MB share plus a remaining 32 MB for the leader.

### COPY FREEZE: docs understate it — the server ERRORs, it does not silently skip (PG 18)
`sql-copy.html` says only "Rows will be frozen **only if** the table being loaded has been created or truncated in the current subtransaction…", which reads as a silent fallback to unfrozen rows. The implementation instead raises `ERROR: cannot perform COPY FREEZE because the table was not created or truncated in the current subtransaction` (string present in `src/backend/po/*.po`, emitted from `src/backend/commands/copyfrom.c`). Slides and migration runbooks that wrap `TRUNCATE` and `COPY … FREEZE` in one transaction are therefore describing a hard requirement, not an optimisation. The docs' other two conditions (no open cursors, no older snapshots held) and the partitioned/foreign-table exclusion are easy to drop when paraphrasing — check for them.

### PG 18 AIO — pre-verified constants (REL_18_6, 2026-09)
Reads only: `PGAIO_OP_WRITEV` exists in `src/include/storage/aio.h` but **no caller invokes `pgaio_io_start_writev`** in 18, so checkpointer/bgwriter/walwriter writes remain synchronous. `io_method` PGC_POSTMASTER, `DEFAULT_IO_METHOD IOMETHOD_WORKER` (`aio.h:42`); options `sync,worker,io_uring` with io_uring conditionally compiled (`aio.c:64`). `io_workers` PGC_SIGHUP, 3/1/`MAX_IO_WORKERS`=32 (`proc.h:460`). `io_max_concurrency` PGC_POSTMASTER, −1/−1/1024; the −1 default is `AioChooseMaxConcurrency()` = `Min(NBuffers/(MaxBackends+NUM_AUXILIARY_PROCS), 64)` (`aio_init.c:97`) — the **64 cap applies to the derived default only**, an explicit setting may go to 1024. `io_combine_limit` PGC_USERSET (exists since 17); `io_max_combine_limit` PGC_POSTMASTER (new in 18); both `DEFAULT_IO_COMBINE_LIMIT = Min(PG_IOV_MAX, 128kB/BLCKSZ)` = 16 blocks = 128 kB. `effective_io_concurrency`/`maintenance_io_concurrency` 1→16 and 10→16 (`bufmgr.h:161-162`); PG 17 docs said "Currently, this setting only affects bitmap heap scans", 18 docs drop that. `pg_aios` = `pg_get_aios()`; io workers are `B_IO_WORKER` → `backend_type = 'io worker'`, ps title `postgres: io worker <n>` (`method_worker.c:414` `set_ps_display`). Note: `SysLogger_Start` runs at `postmaster.c:1077`, `maybe_adjust_io_workers()` at `:1383` — so in real `ps` output **the logger has a lower PID than the io workers**; slide transcripts that list io workers first are wrong.

### PG 18 eager freezing — failure cap is per REGION, not per run (REL_18_6, 2026-09)
Recurring slide error: describing `vacuum_max_eager_freeze_failure_rate` (default 0.03, PGC_USERSET) as "how many pages vacuum may fail to freeze before giving up on the table for that run". Source `src/backend/access/heap/vacuumlazy.c`: the failure budget is `rate × EAGER_SCAN_REGION_SIZE` (4096 blocks = 32 MB) and is **reset on entering each new region** — exhausting it only *suspends* eager scanning until the next region (`eager_scan_remaining_fails`, L402-410). What *permanently* disables eager scanning for the rest of the vacuum is the **success** cap, `MAX_EAGER_FREEZE_SUCCESS_RATE 0.2` of (allvisible − allfrozen) (L235-241, L383-389). Eager scanning is also skipped entirely when `rel_pages < 2 * EAGER_SCAN_REGION_SIZE` = 8192 blocks = 64 MB (L527), for aggressive vacuums, and for tables without sufficiently old tuples — so "on every pass" is an overstatement.

### PG 18 monitoring-view churn worth checking on any DBA slide (2026-09)
`pg_stat_io` gained `read_bytes`/`write_bytes`/`extend_bytes` and **lost `op_bytes`** (which always equalled BLCKSZ), and gained `object = 'wal'` rows. `pg_stat_wal` **lost** `wal_write`, `wal_sync`, `wal_write_time`, `wal_sync_time` (they moved to `pg_stat_io`'s WAL rows; `track_wal_io_timing` now governs `pg_stat_io`). `pg_stat_progress_vacuum` **and** `pg_stat_progress_analyze` both gained `delay_time` (double precision, **milliseconds**, zero unless `track_cost_delay_timing` — PGC_SUSET, default off). `pg_class` gained `relallfrozen`, which `autovacuum.c:3111-3127` uses to scale `autovacuum_vacuum_insert_scale_factor` by the unfrozen fraction (the `autovacuum_vacuum_max_threshold` cap, default 100000000, applies to `vacthresh` only, **not** `vacinsthresh`). Caveat: `pg_stat_io` itself dates from **v16**, not 18 — a "(v18)" label next to it is wrong.

### PG 18 EXPLAIN ANALYZE output changes (version-sensitive, 2026)
Two v18 changes to verify on any EXPLAIN-bearing slide that may have been copied from a pre-v18 transcript: (1) **BUFFERS is auto-enabled with ANALYZE** — `EXPLAIN ANALYZE` shows `Buffers:` lines without `(BUFFERS)`. Release note "Automatically include BUFFERS output in EXPLAIN ANALYZE" (Guillaume Lelarge, David Rowley, commit c2a4078eb). Source: `src/backend/commands/explain_state.c` ~L180 `es->buffers = (buffers_set) ? es->buffers : es->analyze;`. (2) **Actual rows now print with 2 decimals** — `explain.c:1844` formats actual `rows=%.2f` (e.g. `rows=7435.00 loops=1`); estimated rows stay `%.0f` (`explain.c:1799`). A transcript showing integer actual rows (`rows=7435`) is pre-v18. Option parsing moved from `explain.c` to `explain_state.c` in v18 (grep there for BUFFERS/timing/summary defaulting).

### SQL function inlining is a PLANNER step, not the rewriter (PG)
Common slide imprecision: attributing SQL-function inlining to the rewriter alongside view expansion. Views/rules expansion is the rewriter (`query-path.html` "rewrite system... realization of views"). But `inline_function` / `inline_set_returning_function` live in `src/backend/optimizer/util/clauses.c` and `optimizer/prep/prepjointree.c` — i.e. the **planner/optimizer**. Flag IMPRECISE when a slide lists "inlinable SQL functions" under the rewriter stage.
