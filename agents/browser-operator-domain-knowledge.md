### Listing the fields a custom Odoo module added to a stock model: `ir.model.data.search_read` on field xmlids; and `read` of a list with one missing id fails the whole batch (2026-10-01)

On `dataegret.odoo.com` (19.0+e) one read-only `search_read` on `ir.model.data` with domain `['&',['model','=','ir.model.fields'],'|',['module','=like','de\\_%'],['module','=like','dataegret%']]`, `fields:['module','name']`, `limit:3000` returned 316 rows; each `name` is `field_<model with dots as underscores>__<field>` (e.g. `field_sale_order__x_session_ref`, module `de_course_booking`), so one regex per model lists what the module added, including fields that start with neither `x_` nor `de_`. The `\\_` escape made `=like` match a literal underscore; the module's own `id` and `display_name` xmlids appear too and can be ignored. For a single field's existence, `fields_get` with `args:[["<field>"]]` returns `{}` when absent. Separately, a `read` whose id list contains one non-existent id fails as a whole (MissingError), so a bisect-on-error fallback would blame a field; check explicit ids first with `search([['id','in',ids]])` under `{"active_test":false}`.

### Read-only Odoo RPC probe via `browser_evaluate`: a `window` helper survives between calls, and an explicit `filename` saves a BARE JSON array (2026-10-01)

On `dataegret.odoo.com/odoo` (logged-in headless clone), `fetch('/web/dataset/call_kw/<model>/<method>')` and `fetch('/web/session/get_session_info')` from `browser_evaluate` worked with the session cookie alone, no CSRF or header friction (session info gave `uid`, `username` = the login, `db`). A helper object parked on `window` (method allow-list, 0.8 s pacing from the previous request's end, address masking, output buffer) persisted across separate `browser_evaluate` calls as long as the page was not navigated, so a 26-request probe ran as six short calls, one section each (about 8 s per call at most), and a bug in one section would have cost no extra Odoo requests. Return arrays of lines, not one long string (a string pretty-prints as a single JSON string with `\n` escapes). Passing `filename: ".playwright-mcp/<name>.txt"` to `browser_evaluate` wrote a bare pretty-printed JSON array with no `### Result` wrapper (unlike the overflow-to-file case in the entry further down) and returned only a link; `json.load` it and write the final text with Bash instead of retyping, then delete the intermediate. When masking addresses, mask raw strings before `JSON.stringify` (an escaped `\n` leaves a stray `n` in front of the local part) and before any truncation, then re-check the saved file with a lookbehind regex.

### A `sips` crop-and-upscale that "resolves" a two-way digit ambiguity (e.g. 2-vs-8) can still be wrong — a one-digit-per-output-line isolation is the only check that removed all doubt (2026-09-30)

On the SLA browser's odoo.sh web-shell canvas terminal (same xterm-canvas widget documented
elsewhere in this file), re-reading a traceback's line number that a **prior, separate session**
had already recorded as `207` produced a fresh crop-and-upscale that looked equally readable as
either `207` or `287` — a 2-vs-8 confusion, the same glyph-ambiguity family already catalogued
here for 9-vs-0. The standing fallback (spell each digit as an English word via a `sed` chain,
`s/2/ TWO/g; ... s/8/ EIGHT/g`) gave a clean-looking "TWO EIGHT SEVEN" — but a **second**,
independent digit check on an unrelated number in the same session (a different traceback's line
number, expected 4 digits) showed that the word-spelling technique can itself silently drop or
visually merge a word when several digit-words sit close together in a small terminal font (a
4-digit "1116" briefly read back as only "ONE ONE SIX" from one screenshot crop, i.e. only 3
words, before a stricter check found the missing fourth). Given that a *second* technique had
just been caught failing silently, the word-spelling result for the 207-vs-287 case was not
trusted either, even though it looked unambiguous on its own. The check that actually removed all
doubt for both numbers: `grep -oE "[0-9]+" | sed "s/./&\n/g"` — one digit per physical output
line, so the terminal renders each character on its own row with nothing adjacent to blend into,
and the answer is a simple line count (4 lines `1`,`1`,`1`,`6` → 1116; 3 lines `2`,`8`,`7` → 287,
confirming the fresh read and contradicting the older session's `207`). Practical rule: for a
digit that matters enough to cite as evidence, don't stop at the first technique that produces a
readable-looking answer, and don't fully trust the word-spelling fallback either when several
words could sit close together — the one-digit-per-line isolation is strictly more reliable than
either crop-zoom or word-spelling and is worth reaching for directly whenever two different
techniques (or a fresh read vs. an older file) disagree, rather than re-cropping the same
screenshot again. Separately: when a fresh, multiply-disambiguated re-read contradicts a specific
digit in an earlier evidence file, and nothing in the intervening commits could have changed the
source line (confirmed here via both commits' own messages), the fresh reading was reported as
authoritative and the discrepancy flagged explicitly in the new evidence file — the older file was
left untouched rather than silently "corrected" after the fact.

### Wise Business statement wizard: the calendar's "Go to 20 year view" shortcut reaches any month in 2 clicks (year, then month) instead of paging month-by-month; CSV rows never quote the "TransferWise ID" field even though the header cell is quoted (2026-09-29)

Redoing the same 12 Data Egret GmbH statement downloads (Jan-Apr 2026 CSV, May-Aug 2026 CSV+PDF)
with one change from a prior run — ticking "Display transactions with fees shown separately" in
step 4 — surfaced two mechanical shortcuts worth reusing, on top of the wizard structure already
documented below. (1) Every date-picker calendar's month heading (e.g. "September 2026") is
itself a button, "Go to 20 year view" — clicking it swaps the calendar to a year grid (2021-2026
enabled, later years disabled/future), clicking the year swaps to a Jan-Dec month grid for that
year (months after the current one disabled), and clicking the month lands on that month's day
grid. From the wizard's default (current month, September in this run) this reaches January
through August in exactly 2 clicks (year, month) plus the day click — far cheaper than the
"budget one previous-month click per month of distance" guidance from the original 2026-09-29
entry below, which was written before this shortcut was found; use the year-view shortcut first
and only fall back to paging "previous month" if a target year itself isn't visible on the
20-year grid. Separately, when the target end-of-month equals the actual previous calendar month
relative to today, the quick "Last month" radio (step 1) sets both Start date and End date
correctly in a single click, skipping the calendar entirely — confirmed here for August 2026
against a September-29 "today". (2) Both the file-type radio (CSV/PDF/XLSX/etc.) and the two
step-4 checkboxes ("Display transactions with fees shown separately", "Stamp and sign this
document") are real `<input>` elements marked `sr-only` with a wrapping, click-intercepting
`<label>` — clicking the accessibility-tree radio/checkbox ref directly throws a Playwright
"intercepts pointer events" timeout; click the enclosing clickable label/row element instead
(the snapshot's parent `generic [cursor=pointer]` node one level up), which resolves via
`page.locator('label').filter({hasText: ...})` and works reliably. (3) In the downloaded CSV,
the header row's "TransferWise ID" cell is quoted (`"TransferWise ID"`) but every data row's own
value in that column is NOT quoted, even for values containing a hyphen (`FEE-BALANCE-4708977453`,
not `"FEE-BALANCE-4708977453"`) — a naive `grep '"FEE-'` or an awk field match anchored on a
leading quote (`$1 ~ /^"FEE-/`) silently returns zero on every file; match the bare prefix
(`^FEE-`) instead. Confirmed the fee-separation checkbox's actual effect byte-for-byte: the
default presentation's transaction row carries the pre-fee amount with the fee folded into the
description text and a nonzero "Total fees" column (e.g. `-4805.27`, description "...umgetauscht",
no FEE- row at all); the fees-shown-separately presentation splits the same event into the
transaction row at its post-fee amount (`-4782.31`) plus a sibling `FEE-<same-id>` row for the fee
amount alone, description "Wise Charges for: <id>" — this is what accountants mean by "fees as
separate lines," and it is only present when the checkbox is ticked (confirmed zero FEE- rows in
every one of this account's own previously-downloaded default-presentation files, nonzero in every
fee-separated EUR/GBP file for a month with actual conversion/transfer fees).

### odoo.sh install.log: a single ERROR-level log record can split across two physical lines that match *different* grep patterns — don't add their counts, and don't assume one implies the other (2026-09-29)

On builds `38865550`/`38865556` (`dev/ticket-classification-sla` / `dev/slackbot-sla-integration`,
both commit series culminating 2026-09-29), a `psycopg2`/raw-Postgres error surfaced by Odoo's
`odoo.sql_db` always printed as **two consecutive physical lines from one log call**: a header line
with the normal `<ts> <pid> ERROR <db> odoo.sql_db: bad query: b'INSERT INTO …'` shape (matches the
broad `grep -aE " ERROR "` pattern, because of its `21 ERROR` level field), immediately followed by
a **bare continuation line with no timestamp/level prefix at all** — literally `ERROR:  <postgres
message>` starting at column 1 (matches `grep -aE "ERROR: "`/`"FAIL: |ERROR: "` because of its own
leading `ERROR:`, but does **not** match `" ERROR "` since there is no space before the word at the
start of the line). The two grep patterns this project's standard recipe uses
(`" ERROR "` for the raw tally, `"FAIL: |ERROR: "` for named markers) therefore each catch **one**
of the two lines and miss the other — confirmed concretely on both builds by re-running
`grep -anE " ERROR "` and a separate `grep -anE "bad query"` side by side and matching line numbers:
the "bad query" header (2398/2417 in the two builds) appeared only in the first, the "ERROR:
duplicate key" continuation (2399/2418) only in the second, one line apart every time. Practical
consequences: (1) never assume a bare `grep -acE " ERROR "` count and a `"FAIL: |ERROR: "` count
should sum to, or be simply comparable against, the *number of incidents* — one incident can
contribute 1, 2, or 3 lines split unpredictably across the two patterns depending on log level
fields and continuation-line formatting; (2) when reconciling "every ERROR line attributed" against
a brief's own expected line count (e.g. "six known deliberate lines"), check whether the brief is
counting *physical lines in the file* (which would include a bare continuation line regardless of
which pattern matches it) or *pattern-matched hits* — they can legitimately differ by exactly the
number of such split incidents; (3) the tally line itself (`odoo.tests.result: …`) is *also*
logged at `ERROR` level whenever the run has ≥1 error, and matches `" ERROR "` but never
`"FAIL: |ERROR: "` — always check for and separately attribute it before calling any remaining count
"unexplained."

### SLA browser's canvas terminal: `sips --cropOffset` crop math is unreliable in practice — shrink the viewport instead, and never trust pre-existing scrollback as your own command's output (2026-09-29)

On the same odoo.sh web-shell canvas terminal documented elsewhere in this file (confirmed this run to be JupyterLab's own `jp-Terminal` widget — `document.querySelectorAll` turns up classes `lm-Widget jp-Terminal lm-DockPanel-widget`; it's an xterm.js canvas renderer with no `.xterm-rows` DOM text mirror, so `browser_evaluate` can't read scrollback as text either, and no JS handle to the underlying `Terminal` object was found on the DOM node itself), repeated attempts to isolate one screen region with `sips --cropOffset <dy> <dx> -c <h> <w>` (docs imply offsets shift the crop window from the image's own center) produced visibly wrong regions on nearly every attempt — including results inconsistent with either sign convention tried, and one crop that appeared to show the page's tab-bar chrome relocated to the middle of the frame. returned **6** lines. The extra one was a raw PostgreSQL error line — `ERROR:  duplicate key value
violates unique constraint "..."` — logged as the direct continuation of an `odoo.sql_db: bad
query: ...` line from a deliberately-provoked idempotency test (a passing test, not a failure).

contain the literal substring `ERROR: ` that the grep pattern is also hunting for as a unittest
result marker, so it gets swept up as a false-positive extra hit with no accompanying

error message instead) before treating the count as the number of real failures. This is likely
to recur on any build where a test deliberately provokes a raw SQL error as part of an
idempotency/uniqueness check (the same family of "deliberate ERROR-level log line during a
passing test" already documented elsewhere in this file) — expect the marker-grep count to run
one or more lines ahead of the tally's real failed+error count in exactly that situation, and
attribute the excess by checking each extra hit's own surrounding `Starting`-line window rather
than assuming the grep is unreliable or the tally is wrong.

### playwright-persistent browser_evaluate — a large result that overflows to a saved file is NOT itself valid JSON; use json.JSONDecoder().raw_decode() (2026-09-24)

When a `browser_evaluate` result exceeds the token limit, the tool saves it to a `.txt` file whose content is `### Result\n<pretty-printed JSON>\n### Ran Playwright code\n\`\`\`js\n...` — trailing text after the JSON object — so a plain `json.loads(open(path).read().split('### Result',1)[1])` fails with `json.decoder.JSONDecodeError: Extra data`. ### Odoo 19 import wizard — `is_company` boolean not importable via wizard UI (Jun 2026, updated)

In Odoo 19 (saas-19.3), the `res.partner` import wizard does NOT expose the boolean `is_company` field (company vs individual flag) under any label in its field picker — not "Is a Company", "Company Type", "Individual", or "is_company". Exhaustively confirmed via searches for "company", "is_company", "Is a Company", "individual", and "type". The "Company" field in the wizard is a many2one to `res.company` (the owning tenant company), NOT the boolean. The "Address Type" field (from the "type" search) maps to `company_type` selection (contact/delivery/invoice/etc.), also not the boolean. **The boolean `is_company` field is simply absent from the import wizard field list.** Workaround: import without the flag (records land as Individuals), then batch-update via script/API, OR use the Odoo RPC `load()` method directly which respects `is_company`. A CSV column named `is_company` with `True` auto-maps to the wrong "Company" many2one and fails Test with "No matching record found for name 'True' in field 'Company'". Additionally, `base_vat` enforces GB VAT format as `GB123456782` (9 digits); 8-digit values cause a hard blocking Test error.
