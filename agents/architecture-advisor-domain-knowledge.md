### Odoo "Test Mode" on a payment provider is not Stripe test mode (19.0)
`payment.provider.state` is `[('disabled',"Disabled"),('enabled',"Enabled"),('test',"Test Mode")]`, help: "In test mode, a fake payment is processed through a test payment interface." It does **not** swap credentials: `payment_stripe` holds exactly one triplet (`stripe_publishable_key`, `stripe_secret_key`, `stripe_webhook_secret`) with no live/test pair, so live-vs-sandbox is decided solely by which key you paste (`sk_live_` vs `sk_test_`). What `state='test'` actually changes: `_onchange_state_switch_is_published` sets `is_published = (state == 'enabled')`, and `_get_compatible_providers` filters unpublished providers out for non-internal users — so a public/token-only portal buyer sees **no payment button** on a Test-Mode provider unless `is_published` is set True by hand. Switching between test/enabled/disabled archives that provider's saved payment tokens. A Stripe-Connect-onboarded provider can never be set to Test Mode (`_check_state_of_connected_account_is_never_test`), and Apple Pay domain registration rejects test keys.

### Stripe Tax vs Odoo 19: reverse-charge gating is the real difference (2026-08)
Both compute EU B2B reverse charge, but on different evidence. Stripe: "Wenn Sie Stripe Tax verwenden und Ihr Kunde eine Steueridentifikationsnummer angibt, wendet Stripe Tax … die Umkehrung der Steuerschuldnerschaft oder den Nullsatz an, solange die Steueridentifikationsnummer **unabhängig von ihrer Gültigkeit** dem erforderlichen Zahlenformat entspricht" (docs.stripe.com/tax/invoicing/tax-ids, /tax/checkout/tax-ids) — VIES validation runs async afterwards and does not retro-correct the collected tax. Odoo 19 gates it: `base_vat/models/res_partner.py::_get_vat_required_valid` ANDs `vies_valid` into fiscal-position matching when `company.vat_check_vies` is on, so a `vat_required` position (reverse charge) only auto-applies on a VIES-valid number; `vies_valid` is True only for IAP status `valid` (`/api/vies/1/check_validity`, statuses valid/pending/fault/unassigned, async webhook + `_cron_check_vies_iap`), so outages and "pending" fail closed to charging domestic VAT. Stripe's invoice PDF prints "Umkehr der Steuerschuld (Reverse Charge)" when exemption is `reverse`; Odoo's equivalent surface is `account.tax.invoice_legal_notes` (Html, "Legal mentions that have to be printed on the invoices", present in 19.0).

### EU VAT on live-streamed/virtual events since 2025-01-01 — and why no tax engine settles it
Directive (EU) 2022/542 extended Art 54 so B2C virtual attendance of educational/cultural events is taxed where the consumer resides; B2B follows reverse charge. Advisers note the €10,000 micro-business threshold in Art 59c covers only Art 58 TBE services, so it does **not** shelter virtual-event supplies — cross-border B2C can create an obligation from the first sale (grantthornton.nl, marosavat.com, vatcalc.com). Stripe's own guide states the 2025 rule, but its EU technical doc still says remotely-performed services to EU individuals are "taxable in the seller's country" and event admission is taxable "where the venue is located" — neither expresses Art 54 for a venue-less live stream, and the relevant tax code `txcd_20060045` ("Training Services - Live Virtual") has no documented per-country behaviour. Practical consequence: the classification (Art 54 event vs Art 58/45 remote service) is a Steuerberater question, and the tooling question reduces to which system can *express* the answer. Odoo can (fiscal positions per country; `l10n_eu_oss` auto-creates `OSS B2C <Country>` positions with `auto_apply`, sequenced after the EU B2B position); Stripe Tax's determination is not overridable per jurisdiction except via a preview-stage manual-rules fallback that only fires when automatic calculation cannot compute.

### Stripe Invoicing emits no EN 16931 e-invoice; Germany's issuance mandate lands 2027/2028
Stripe: "Stripe Invoicing erstellt Rechnungsdatensätze … **generiert oder überträgt jedoch nicht selbst rechtskonforme E-Rechnungsdateien**" — you must add a Marketplace app (preferred partner Billit) or a webhook integration to a provider (docs.stripe.com/invoicing/e-invoicing). Germany (Wachstumschancengesetz): receiving structured EN 16931 invoices for domestic B2B mandatory since 2025-01-01; **issuing** mandatory 2027-01-01 above €800k turnover and 2028-01-01 for everyone; formats XRechnung / ZUGFeRD, decentralised exchange, no clearance platform. Odoo 19 Enterprise ships Factur-X (PDF/A-3) plus Peppol sending with BIS Billing 3.0 / XRechnung CIUS, and DATEV ATCH + DATEV DATA exports with GoBD certification. Any design that moves invoice issuance out of Odoo inherits the 2027/28 mandate as a second integration.

### Odoo 19 `payment_stripe` sends a bare PaymentIntent — Stripe Tax cannot see the sale
Verified in `addons/payment_stripe/models/payment_transaction.py` (19.0): `_stripe_prepare_payment_intent_payload()` posts to `payment_intents` with `amount` = the Odoo transaction total, `currency`, `description` = the transaction reference, capture method and payment-method type. No line items, no product tax code, no `hooks[inputs][tax][calculation]`. So with Odoo as the payment surface, Stripe Tax is structurally out of the loop; wiring it in means calling `/v1/tax/calculations` first and overriding that method (its docstring already calls it "a hook for modules that would fully implement Stripe Connect"), and Stripe requires the PaymentIntent amount to equal the calculation total — i.e. Odoo's tax lines must already agree with Stripe's, which is a two-way sync, not a delegation.

### Slack Socket Mode vs HTTP — production stance (2026-07)
Slack docs: "we recommend using HTTP for production applications" for highest reliability, but "As long as you do not intend to submit your app to the Slack Marketplace and actively maintain your connection … Socket Mode is a reliable option." Limit: 10 concurrent WebSocket connections per app. Marketplace/distributed apps MUST use HTTP. No deprecation signals. `bolt-python` `SocketModeHandler` defaults `auto_reconnect_enabled=True`; historical edge-case reconnect bugs (bolt-python #470, python-slack-sdk #1379). Socket→HTTP switch under Bolt = swap adapter + stand up public endpoint + signature-verify; listener logic unchanged. Source: docs.slack.dev/apis/events-api/comparing-http-socket-mode/.

### Slack Connect external-member interaction matrix
App installed only in the host workspace, channel shared via Slack Connect: external members CANNOT invoke slash commands or message actions ("not shared — limited only to the team that has installed the app"); they CAN click buttons/dropdowns (validate `authorized_users` in the interaction payload); bot users can DM external users who share a channel; `app_mention` fires for external members' mentions. Ephemeral delivery (`chat.postEphemeral`) and button-triggered modals (`views.open`) to external members are NOT confirmed by docs — test in the real workspace. Source: docs.slack.dev/apis/slack-connect/.

### WordPress deploy architecture for code-only pipelines
When only the theme / mu-plugins are git-managed and content + plugins live in wp-admin, rsync-over-SSH beats containers or Bedrock — the immutable slice is too small to justify either. The mutable runtime state (DB, uploads, ad-hoc-installed plugins) dominates and neither tool addresses it.
