### Calendar/Tasks read-write scopes are SENSITIVE not restricted → no CASA (verified 2026-06-29)

Read-write scopes: Calendar `https://www.googleapis.com/auth/calendar` ("See, edit, share, and permanently delete all the calendars you can access") and `…/auth/calendar.events` ("View and edit events on all your calendars"); Tasks `…/auth/tasks` ("Create, edit, organize, and delete all your tasks"). `…/auth/calendar.app.created` = create/manage only secondary calendars the app made (narrowest write). All Calendar + Tasks scopes are **sensitive**, never **restricted** — the restricted list is Gmail, Drive, Fit, Chat, Data Portability, Photos, Health only (support.google.com/cloud/answer/13464325). Therefore the annual third-party security assessment (**CASA**, App Defense Alliance) is **NOT required** for a Calendar/Tasks read-write app — CASA is restricted-scope-only. Sensitive verification = scope justification + Unlisted YouTube demo video, up to ~10 business days (developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification). Beware third-party blogs that wrongly lump Calendar into "CASA-required restricted scopes."

### Internal user type bypasses ALL scope review; External+verified lifts 7-day token expiry + 100 cap (verified 2026-06-29)

Internal user type (single Workspace/Cloud Identity org): "use of restricted or sensitive scopes doesn't require further review by Google", no unverified-app screen, no 100-user cap, no 7-day refresh-token expiry (support.google.com/cloud/answer/13464323; developers.google.com/workspace/guides/configure-oauth-consent). Only available when ALL users share one Workspace org. External + Testing: hard cap 100 test users, unverified-app warning, refresh token expires **7 days** after consent (developers.google.com/identity/protocols/oauth2#expiration, verbatim "publishing status of 'Testing' is issued a refresh token expiring in 7 days, unless the only OAuth scopes requested are a subset of name, email address, and user profile"). External + Production + verified removes the 7-day expiry, the warning, and the cap. Installed-app client secret is "obviously not treated as a secret" (RFC 8252 public client); PKCE + loopback (127.0.0.1) is the sanctioned flow — acceptable for a verified public desktop app; the shipped client_id/secret is not a confidentiality boundary, only a quota/branding identity.

### Recurring-event write semantics + write safety mechanics (verified 2026-06-29)

events.insert/update/patch/delete/move. update = full replace (no patch semantics); patch = partial but costs **3 quota units** (prefer get+update). Edit ALL instances → patch the parent recurring event by its `eventId`. Edit ONE instance → `events.instances` to get the instance (has own id, `recurringEventId` points to parent, `originalStartTime` identifies the slot), patch that instance. "This-and-following" is **not native**: truncate parent `RRULE` with `UNTIL` before target + `events.insert` a new recurring event for the remainder (resets exceptions after the split). `sendUpdates` enum = `all` / `externalOnly` / `none` (attendee notifications). Client-generated event `id` on insert: base32hex (a-v, 0-9), 5–1024 chars, unique per calendar, RFC 4122 UUID recommended → gives create idempotency. Optimistic concurrency via ETag + `If-Match` (get first, send the etag). move only `default` event type, changes organizer. Docs: developers.google.com/workspace/calendar/api/v3/reference/events{,/insert,/instances}, /api/guides/recurringevents.

### Console UI rename + consent-screen facts (verified 2026-06-08)

The old "OAuth consent screen" is now **APIs & Services > Google Auth Platform**, split into tabs **Branding / Audience / Clients / Data Access** (renamed ~2024; first visit shows **Get Started**). Scopes are added under **Data Access > Add or remove scopes**; test users under **Audience > Test users > Add users**. Both `calendar.readonly` and `tasks.readonly` are **sensitive** scopes (sensitive-scope verification ~3-5 business days; needed only when published to Production for non-test users). External + Testing publishing status: refresh tokens expire **7 days** after consent (exception: only name/email/profile/openid scopes); test-user cap is **100**. Brand verification (logo/name on consent screen, 2-3 business days) is separate from scope verification. Desktop-app client secret is downloadable only at creation time; redirect URIs are not user-editable for Desktop type (loopback handled automatically). Docs: developers.google.com/workspace/guides/configure-oauth-consent, developers.google.com/identity/protocols/oauth2#expiration, support.google.com/cloud/answer/15549257.

### Seed: installed-app loopback flow, read-only scopes, multi-account free/busy (seeded 2026-06-08)

Desktop apps use the **loopback redirect** (`http://127.0.0.1:<port>`), not the deprecated OOB flow; pair with PKCE + a `state` nonce. Get a refresh token only with `access_type=offline` + `prompt=consent` on first authorization — persist it per account as a secret at rest. Read-only viewing = `calendar.readonly` + `tasks.readonly`. For "when am I free" across accounts: union each account's busy intervals; `freebusy.query` is cleaner than `events.list`+merge when you don't need event detail, but it returns no detail and caps calendars per call. `events.list` with `singleEvents=true&orderBy=startTime` expands recurrences in order; all-day uses `date`, timed uses `dateTime`+`timeZone`. Incremental sync via `nextSyncToken`; a `410 Gone` means discard the token and full-resync. (Verify all against live `developers.google.com` docs each run — Google deprecates and renames.)
