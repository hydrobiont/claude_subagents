### Comparing a framework's source across two release tags: extract the function, not the file (2026-09)
Whole-file hashes lie about "unchanged": `django/db/backends/postgresql/base.py` differs between tags `5.2` and `6.1` (23486 vs 23829 bytes) while `get_connection_params()` is byte-identical — so slice the function by indentation and hash *that* before writing "identical at both tags". Frameworks hide the pooler-relevant behaviour in code and never document it: Django's `get_connection_params()` forces `conn_params["prepare_threshold"] = conn_params.pop("prepare_threshold", None)` ("Disable prepared statements by default to keep connection poolers working") and its default cursor is `class Cursor(CursorMixin, Database.ClientCursor)` against `class ServerBindingCursor(CursorMixin, Database.Cursor)`, yet `/en/5.2/ref/databases/` and `/en/6.1/` have **zero** occurrences of "prepared statement" or `prepare_threshold`; Rails' three-way protocol-`Close` condition is only the `if PG::Connection.method_defined?(:close_prepared)` guard plus `supports_close_prepared?` → `database_version >= 17_00_00` in `postgresql_adapter.rb`. Fetch with `curl raw.githubusercontent.com/<org>/<repo>/<tag>/<path>` — **psycopg.org answers automated fetches with HTTP 403**, so read Psycopg docs as `.rst` from `raw.githubusercontent.com/psycopg/psycopg/<tag>/docs/…` (better citations anyway: `docs/basic/from_pg2.rst @ 3.3.5`). Django's own version axis is split across two pages: the PostgreSQL/psycopg floors are in `/en/<ver>/ref/databases/`, the LTS designation and latest release only in the support table at `https://www.djangoproject.com/download/`.

### PgBouncer's feature map has two columns, lives outside the release cycle, and warns about nothing (2026-09)
`features.md` (in `pgbouncer/pgbouncer.github.io`, not the main repo) covers **Session pooling** and **Transaction pooling** only — a statement-pooling column has to be derived and separately sourced from `doc/config.md` § `pool_mode` ("Transactions spanning multiple statements are disallowed in this mode") plus `src/server.c`, where a non-idle ReadyForQuery under `POOL_STMT` calls `disconnect_server(server, true, "transaction blocks not allowed in statement pooling mode")` — a disconnect, not an error. The table barely moves: last content change 2023-11-06, the prepared-plan row flipped `No [^2]` → `Yes` in `5e8aa1d` on 2023-11-02, three weeks *after* 1.21.0 shipped, and the advisory-lock row arrived in `b57fa0b` (2021-07-09, closing pgbouncer#617) — so date a row by `git log -- features.md`, never by the site's release tag. Footnote `[^0]`'s six startup parameters = the five hard-coded in `src/varcache.c:init_var_lookup()` (`DateStyle`, `client_encoding`, `TimeZone`, `standard_conforming_strings`, `application_name`) plus `track_extra_parameters`, default `IntervalStyle`; a parameter is trackable only if PostgreSQL reports it, which is why `SET ROLE` can never be restored (`role` carries no `GUC_REPORT` flag in `guc_tables.c`). And PgBouncer parses no client SQL at all — `src/client.c:handle_client_work()` dispatches on packet type, and the only statement-text comparison is against the *server's* `CommandComplete` tag (`"DEALLOCATE ALL"` / `"DISCARD ALL"`, since 1.22.0) — which is why issue #976, "warn/error when unsupported features are used", is still open.

### Moving a scratchpad lab into the base: copy the evidence, excerpt the log, relativize the paths (2026-09)
A lab built in the session scratchpad dies with the session, so promote it to `labs/<YYYY-MM-DD>-<slug>/` before the run ends — but copy only the evidence: `RESULTS.md`, the `ini/`, `scenarios/`, `out/` and per-run logs, and the harness scripts. Leave out the built trees, the `pgdata` and the source exports (~500 MB against 350 KB of evidence here) and say so in the lab `README.md`. A server log captured at `log_min_duration_statement = 0` is unusable whole (79 MB, 420k lines): write `logs/<name>.log.excerpt` holding only the passages the articles cite, each labelled with its line range in the original, and repoint the `Files` section of `RESULTS.md` at it. Rewrite absolute paths in the `.ini` files and scripts to be relative — `LAB=$(CDPATH= cd -- "$(dirname -- "$0")" && pwd)` for sh, `os.path.dirname(os.path.abspath(__file__))` for Python — and make the ini generator emit relative `auth_file`/`logfile`/`pidfile` too, so regenerating reproduces the committed files byte for byte; that diff is a one-command check that the harness still matches the evidence. Do **not** rewrite captured tool output (`initdb.log`, pgbench's `transaction type:` line): it is evidence, and the README explains why an absolute path survives in it.

### Batch-editing the base from Bash: three traps, and the frontmatter checker (2026-09)
Sweeping all articles at once (a citation-form change, a spelling normalization) is the efficient move, but three things bite. **zsh does not word-split unquoted parameters**, so the habitual `G='git -C /path'; $G show …` runs a command literally named `git -C /path` and every result comes back empty — repeat the full command or use a function, and never trust an all-empty loop result without checking one case by hand. **`perl -pi -e` interpolates the replacement**, so any `$(…)`, `$0` or `$1` in new script text is silently mangled (`LAB=$(dirname …)` became `LAB=20 20 12 …`); do structural rewrites in Python with plain `str.replace` plus an `assert old in s` per edit. And **PyYAML is not installed while Ruby is**: `ruby -ryaml -e 'YAML.load_file(ARGV[0])'` over the extracted `---` blocks is the frontmatter parse check, and it doubles as a schema check (compare `d.keys` against the expected set, count `sources`, assert every `kind: lab` ref). Finish by machine-checking that each `INDEX.md` row equals the file's actual frontmatter — a run brief's row table is a report, not the source of truth.

### Verifying driver-documentation claims: fetch raw, pin to a release tag, know who documents in code (2026-09)
A driver's own documentation is the primary source for its knobs, so quote it verbatim: `curl`/`urllib` from Bash reaches the network here and returns the real page, where `WebFetch` returns a summary you cannot quote. Sphinx (psycopg, asyncpg), docfx (Npgsql), hexdocs (Postgrex), pkg.go.dev (pgx), Django, Rails guides and the PHP manual all render server-side and strip to text cleanly; **metacpan.org is behind a Cloudflare challenge** — read CPAN POD at `https://fastapi.metacpan.org/source/<AUTHOR>/<DIST-VERSION>/<file>` and get the current version from `https://fastapi.metacpan.org/v1/release/<Dist>`. Several projects document a knob only in code (Rails `prepared_statements` / `statement_limit` / statement names, Postgres.js in its README, DBD::Pg in Pg.pm's POD): cite `raw.githubusercontent.com/<org>/<repo>/<tag>/<path>` at a **release tag**, never `master`, and date a behaviour change by diffing the same file at two tags (that is how "Rails sends protocol `Close` from 8.1.0, `DEALLOCATE` in 8.0.x" was pinned). Driver pages are mostly unversioned and drift, so a driver table justifies `confidence: medium` even when every row was checked.

### An article about the *absence* of a tool feature is scoped by configuration, not by a release range (2026-09)
When an ecosystem article documents what happens **without** a feature (PgBouncer with no prepared-statement tracking), `ecosystem_versions` is `"all"`, not `"<1.21.0"`: the condition survives the feature's release because a setting can switch it off (`max_prepared_statements = 0`), and a reader on the newest release needs the hit. Carry the real scope in the body instead — name both halves at every claim ("before 1.21.0, or any release running with the setting at 0") — and send the reader to the tool's own runtime view (`SHOW CONFIG` prints value beside built-in default) rather than to a release default, since distributions and managed services override defaults in both directions and vendor numbers are not verifiable from the project's sources.

### PgBouncer stats: every SHOW variant renames the same counters, and no RESET exists (2026-09)
`src/stats.c` is the authority for admin-console statistic column *names*, and each command spells them differently: `SHOW STATS` → `total_client_parse_count` / `avg_*`, `SHOW STATS_TOTALS` → the bare `client_parse_count` (despite `doc/usage.md` calling it "the total values (**total_**)"), `SHOW STATS_AVERAGES` → `avg_*`, and `SHOW TOTALS` → `total_ps_client_parse_count`, because its `WTOTAL(name)`/`WAVG(name)` macros paste the prefix onto the raw `PgStats` field names, which carry the internal `ps_` prefix. Never assume a counter keeps its name across variants — read the `pktbuf_write_RowDescription` argument list in `src/stats.c` for that command. `src/admin.c` `cmd_list[]` is the complete list of non-`SHOW` admin commands: at `pgbouncer_1_25_2` only disable, enable, kill, kill_client, pause, reconnect, reload, resume, select, show, shutdown, suspend, wait_close — **there is no RESET/RESET STATS**, so totals are cumulative since process start (`doc/usage.md`: "the total figures are since process start, the averages are updated every `stats_period`", default 60 in `src/main.c`) and only a restart zeroes them. Per-connection `prepared_statements` in `SHOW SERVERS`/`SHOW CLIENTS` is `HASH_COUNT()` in `src/admin.c`, since 1.21.0; the parse/bind counters only since 1.24.0 (PR #1192). A column's existence at a release is settled by grepping `doc/usage.md` at the tag — it tracks the code reliably.

### Which PostgreSQL GUC exposes extended-protocol steps, and what is never logged (2026-09, PG 18)
For any article on protocol-level prepared statements — poolers especially — these visibility rules are worth not re-deriving. `log_min_duration_statement` / `log_duration` produce the three-line `duration: N ms  parse|bind|execute <name>: <sql>` triplet: `exec_parse_message()`, `exec_bind_message()` and `exec_execute_message()` in `src/backend/tcop/postgres.c` each gate their own line on `check_log_duration()`. `log_statement = 'all'` does **not** — it runs through `check_log_statement()`, called only from `exec_simple_query()` and `exec_execute_message()`, so an extended-protocol client yields one `execute <name>: <sql>` line per execution and nothing for Parse or Bind (docs, `runtime-config-logging`: "For clients using extended query protocol, logging occurs when an Execute message is received"). A protocol `Close` (`'S'`) is **never** logged at any setting: `PostgresMain()`'s `case PqMsg_Close:` calls `DropPreparedStatement()` and `pq_putemptymessage(PqMsg_CloseComplete)` with no `ereport` — a pooler's LRU eviction is therefore invisible server-side and must be inferred from the pooler's own counters. There is no `exec_close_message()` function; the handler is inline in the `PostgresMain()` message loop.

### Reading the PostgreSQL checkout by tag, and the zsh `$t:path` trap (2026-09)
`sources/postgresql/` carries all 690+ release tags plus `REL_17_STABLE`/`REL_18_STABLE`, so never switch branches: read with `git show REL_18_STABLE:<path>`. Per-version facts (catalog column sets, when a string first appeared) are settled offline by reading the release tag directly — `git show REL_15_0:src/include/catalog/pg_proc.dat` — and "which major first shipped commit X" by `git tag --contains <commit> | grep -E '^REL_?[0-9]+(_[0-9]+)?_0$' | sort -V | head -1`. Old release notes are in-tree too (`doc/src/sgml/release-NN.sgml` at `REL_NN_0`; pre-10 in `release.sgml`), so release-note items can be quoted without a web fetch. Two traps: in **zsh**, `git show "$t:src/..."` inside a loop fails with "bad substitution" or silently prints the commit — always brace it, `"${t}:src/..."`; and writing temp files to `/tmp` can silently produce nothing, use the session scratchpad. An honest `applies_to` lower bound costs one grep: check the identifier or error string at `REL9_2_0`/`REL_13_0` instead of writing `all`.

### Prepared-statement ground truth: the four files (2026-09, verified 17.11 / 18.6)
`src/backend/commands/prepare.c` holds the per-backend `prepared_queries` hash table, `StorePreparedStatement()` (42P05) and `FetchPreparedStatement()` (26000), `DropAllPreparedStatements()`, and the `pg_prepared_statement()` SRF behind the view. `src/backend/tcop/postgres.c` holds `unnamed_stmt_psrc`, `exec_parse_message()` / `exec_bind_message()` / `exec_describe_statement_message()` / `exec_execute_message()`, and the `case PqMsg_Close:` (a missing name is a no-op, CloseComplete always sent) and `case PqMsg_Sync:` blocks in `PostgresMain()`. `src/backend/utils/cache/plancache.c` holds `choose_custom_plan()` (the five-custom-plan rule), `cached_plan_cost()` (the `1000.0 * cpu_operator_cost * (nrelations + 1)` planning charge), `ResetPlanCache()` and `RevalidateCachedQuery()` (which deliberately keeps `generic_cost` / `total_custom_cost`). `src/backend/commands/discard.c:DiscardAll()` is the nine-call `DISCARD ALL` list. The whole set was semantically unchanged 17 → 18.

### Ecosystem articles need a second version axis in the frontmatter (2026-09)
An article about a tool in PostgreSQL's environment carries two independent version axes: `applies_to` stays the **PostgreSQL** range, and the tool's own range goes in extra fields — `ecosystem: <tool>` plus `ecosystem_versions: ">=1.21.0"` — so the answerer can match "PgBouncer 1.23 with PostgreSQL 17" without parsing prose. `applies_to: "all"` is the honest value when the tool speaks a protocol every supported server implements (PgBouncer opens server connections with protocol 3.0); justify it in the body with the citation instead of leaving "all" unexplained. Keep every behavioural claim double-scoped: the tool release *and* the PostgreSQL major.

### External sources sit at differing proximity to PostgreSQL; near-axis ones invert the risk (2026-06)
Two `external` sources now exist with very different proximity to the PG axis. #6 (Brendan Gregg, OS/Linux performance) is *off-axis* — its content is plainly not PG. #7 (Use The Index, Luke! / Markus Winand, `https://use-the-index-luke.com/`, free web edition of *SQL Performance Explained*; cross-DB: Oracle, PostgreSQL 9.0–17, SQL Server, MySQL, Db2) is *near-axis* — SQL indexing/optimization methodology (B-tree anatomy, WHERE access vs. filter predicates, join algorithms, clustering/index-only scans, pipelined ORDER BY, top-N). Key rule: the closer an external source overlaps PostgreSQL, the MORE its content looks PG-applicable and the more tempting it is to quote as PG truth — so the "verify PG-specifics against sources 1–4" discipline matters *more* for a near-axis source, not less. Proximity never promotes a source up the ranking; authoritative only for methodology/concepts, never for a PG default/GUC/catalog/plan-shape/version claim. The four-tier ranking stays PG-only.

### External (non-PostgreSQL) trusted sources use `kind: external` and a separate authority axis (2026-06)
The registry spans "PostgreSQL and the technologies in its environment." Non-PG expert references (first one: Brendan Gregg's systems-performance site, source #6, OS layer) get `kind: external` and are authoritative *only within their stated domain* — they sit BESIDE the PG sources (1–4), never above them for a PostgreSQL claim. The four-tier authority ranking is PG-only; external sources are off-axis.
